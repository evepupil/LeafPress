# 工作流 · 工作流框架

> 模块定位：步骤编排、暂停与恢复、上游改动后作废重跑 · 对应代码：`src/workflows/` · 所属里程碑：[M0 地基](../roadmap.md#m0-地基) · 状态：开发中 · 最近更新：2026-10-05

## 职责与边界

- 管：按顺序执行工作流的步骤；遇到 AI、确认、交接、手动步骤时停下并说明在等什么；恢复时从停下的地方继续；上游输入文件变了就从变动处往后作废重跑；失败可重试；防止两个进程同时跑同一次运行；取消。
- 不管：具体工作流的业务（M1 起逐个加）；数据怎么落盘（通过 `RunStore` 接口，SQLite 实现在记录库）。

## 结构与数据流

接口定在 `src/workflows/types.ts`，不得修改。

| 文件 | 导出 | 说明 |
|---|---|---|
| `src/workflows/engine.ts` | `createWorkflowEngine(deps)`、`WorkflowEngine`、`EngineDeps`、`RunDetail` | 引擎 |
| `src/workflows/run-id.ts` | `newRunId(now)` | 运行编号 |
| `src/workflows/memory-store.ts` | `createMemoryRunStore(options?)` | `RunStore` 的内存实现，单测和试运行用 |
| `src/workflows/catalog.ts` | `WORKFLOWS` | 正式工作流列表，M0 为空数组 |

```ts
interface EngineDeps {
  store: RunStore;
  workflows: readonly WorkflowDefinition<any>[];
  runsDir: string; // <数据目录>/runs
  now?: () => Date; // 缺省 () => new Date()
  newRunId?: (now: Date) => string; // 缺省 newRunId
  staleAfterMs?: number; // 运行中超过多久没动静算异常，缺省 10 分钟
  maxRewinds?: number; // 一次推进里最多回退几次，缺省 20
}

interface RunDetail extends RunReport {
  steps: StepRecord[];
}

interface WorkflowEngine {
  start(workflowId: string, rawParams: unknown): Promise<RunReport>;
  resume(runId: string, input?: ResumeInput, options?: { force?: boolean }): Promise<RunReport>;
  cancel(runId: string): RunReport;
  show(runId: string): RunDetail;
  list(filter?: { states?: readonly RunState[] }): RunRecord[];
}
```

### 构造时检查

`createWorkflowEngine` 时检查每个工作流：编号不重复；步骤编号在工作流内不重复，且符合 `^[a-z][a-z0-9-]*$`（要拿来当目录名）。不符合抛 `LeafPressError("INTERNAL")`。

### 运行编号

`newRunId(now)` 返回 `YYYYMMDD-HHmmss-xxxx`：日期时间取本地时间，`xxxx` 是 4 位小写字母或数字的随机串。比如 `20261005-201530-k3x9`。人能看懂是哪天跑的，也基本不会撞。

### start

1. 找工作流，找不到抛 `WORKFLOW_UNKNOWN`。
2. `params = parseParams(rawParams)`，不合法时它自己抛 `USAGE`，原样往外抛。
3. 生成编号，建运行目录 `<runsDir>/<runId>`。
4. `store.createRun`：状态 `running`、游标 0；每个步骤一条记录，状态 `pending`、`attempts` 0、`inputHashes` 为 `{}`。
5. 进入「推进」。

### resume

1. 读运行，不存在抛 `RUN_NOT_FOUND`。
2. 已完成或已取消：抛 `RUN_STATE_CONFLICT`，message「这次运行已经结束」。
3. 运行中：带了 `force` 且 `updatedAt` 距现在超过 `staleAfterMs`，视为上次异常退出，接管继续；否则抛 `RUN_STATE_CONFLICT`，hint「如果确定上次是异常退出，等 10 分钟后加 --force」。
4. 等待中或失败：`store.transitionRun(runId, ["waiting", "failed"], "running", { error: null })`，返回 false 时抛 `RUN_STATE_CONFLICT`（说明另一个进程抢先恢复了）。**必须在任何 await 之前完成这一步**，才能保证同时到来的两次恢复只有一个成功。
5. 作废检查：按序号检查所有状态为 done 的步骤，对它 `inputHashes` 里记录的每个路径重新算哈希（`sha256File`，文件不存在为 `"absent"`），只要有一个对不上，就把这一步和它后面的所有步骤重置为 pending（清空 outputs、wait、error、startedAt、finishedAt、inputHashes，保留 attempts），游标设到这一步。
6. 如果游标所在步骤原本是等待中（且没被第 5 步重置），这次执行它时把 `input` 作为 `ctx.resume` 传入；其他情况不传。
7. 进入「推进」。

### 推进（start 和 resume 共用）

循环，直到游标越过最后一步或遇到停下的情况：

1. 取游标处的步骤定义和记录；建步骤目录 `<runDir>/<stepId>`。
2. `updateStep`：状态 running，`attempts` 加 1，`startedAt` 为当前时间，清空 error 和 wait。
3. 组装 `ctx`：`outputs` 只包含状态为 done 的步骤的输出（按步骤编号）；`resume` 只在上面第 6 条的情况下有。
4. 执行 `run(ctx)`；它抛出的异常转成「失败」，错误文字是 `LeafPressError` 的 message，其他异常为「内部错误：」加异常的 message，不带调用栈。
5. 按结果处理：

| 结果 | 处理 |
|---|---|
| done | 调 `inputFiles(ctx)` 拿输入文件，逐个算哈希；`updateStep` 为 done，写入哈希、outputs（缺省 `{}`）、`finishedAt`；游标加 1，`updateRun` 写游标 |
| wait | `updateStep` 为 waiting 并写入 wait；`updateRun` 状态 waiting；返回报告 |
| fail | `updateStep` 为 failed 并写入 error、`finishedAt`；`updateRun` 状态 failed 并写入 error；返回报告 |
| rewind | 目标步骤必须存在且序号不大于当前，否则按失败处理（「回退目标无效」）；回退次数加 1，超过 `maxRewinds` 按失败处理（「回退次数过多，可能陷入循环」）；把目标到当前的所有步骤重置为 pending（规则同作废检查）；游标设为目标，`updateRun` 写游标，继续循环 |

6. 全部完成：`updateRun` 状态 completed、清空 error，返回报告。

推进过程中记录库自己抛出的错误不拦截，直接往外抛（运行会停在 running，之后可以用 force 接管）。

### cancel、show、list

- `cancel`：`transitionRun(runId, ["waiting", "failed"], "cancelled")`；运行不存在抛 `RUN_NOT_FOUND`，状态不对抛 `RUN_STATE_CONFLICT`。
- `show`：报告加全部步骤记录；不存在抛 `RUN_NOT_FOUND`。
- `list`：直接转给 `store.listRuns`。

### 报告

`RunReport` 的 `currentStep` 和 `wait`：等待中时是游标处的步骤和它的等待请求；失败时是失败的步骤（无 wait），并带上 error；完成、取消时都没有。

### 内存存储 `createMemoryRunStore`

完全照 `RunStore` 的注释实现：读回的是拷贝（外部改了不影响存储内容）；空值是「字段不存在」；`transitionRun` 同步完成比较和修改；更新时刷新 `updatedAt`（时间可注入）。

## 关键决策

1. 引擎只认 `RunStore` 接口，内存和 SQLite 两种实现跑同一套约定测试，引擎的单测不依赖数据库。
2. 恢复时的「比较并交换」放在第一个 await 之前：JavaScript 单线程，同步完成的检查和修改不会被同一进程里的其他恢复插队；跨进程则靠 SQLite 的条件更新保证。
3. 作废检查用「完成时记下的输入文件路径」重新算哈希，不再调用 `inputFiles`：判断依据和当时完全一致。
4. 回退次数只在一次推进内计数：跨越多次恢复的回退都经过作者，不会无人值守地死循环。

## 验证方式

单测放在 `tests/workflows/`，用内存存储和临时目录，时间和编号都注入。用测试里自定义的小工作流覆盖：

1. 全是代码步骤：一次跑完，后一步能拿到前一步的输出，步骤目录都已建好。
2. AI 步骤：先停下（状态 waiting、报告带任务文件路径）；恢复后这一步拿到 `ctx.resume`，完成后继续。
3. 确认步骤：同意则继续；驳回时步骤返回 rewind 回到前面某一步，从那一步重跑。
4. 失败：报告带错误；恢复时重跑失败的那一步，`attempts` 变成 2，成功后完成。步骤抛异常同样按失败处理，错误文字里没有调用栈。
5. 作废：A 步骤写出文件并把它列为 B 步骤的输入，C 步骤停下；改动这个文件后恢复，B 被重置并重跑、C 再次停下；文件被删掉也算改动。
6. 恢复已完成、已取消的运行抛 `RUN_STATE_CONFLICT`；恢复运行中的运行，不带 force 抛错，带 force 但没超时也抛错，带 force 且超时则接管。
7. **并发**：对同一个等待中的运行同时发起两次恢复（`Promise.allSettled`），恰好一个成功、一个抛 `RUN_STATE_CONFLICT`。
8. 取消：等待中的可以取消；已完成的不行；取消后不能恢复。
9. 未知工作流、参数不合法、步骤编号重复或不合规。
10. rewind 目标无效、回退超过上限都按失败处理。
11. `newRunId` 的格式。
12. **工作流存储约定**：新建 `tests/workflows/memory-store.test.ts`，调用 `tests/contracts/run-store.contract.ts` 的 `describeRunStoreContract("内存存储", () => createMemoryRunStore())`，全部通过。约定测试文件不许改。

`pnpm gate` 全部通过。
