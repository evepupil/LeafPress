# 工作流 · 工作流框架

> 模块定位：步骤编排、暂停与恢复、上游改动后作废重跑、执行权保护 · 对应代码：`src/workflows/` · 所属里程碑：[M0 地基](../roadmap.md#m0-地基) · 状态：开发中 · 最近更新：2026-10-05

## 职责与边界

- 管：按顺序执行工作流的步骤；遇到 AI、确认、交接、手动步骤时停下并说明在等什么；恢复时从停下的地方继续；输入文件变了就从变动处往后作废重跑；失败可重试；保证同一时刻只有一个进程推进同一次运行；异常退出后的接管；取消。
- 不管：具体工作流的业务（M1 起逐个加）；数据怎么落盘（通过 `RunStore` 接口，SQLite 实现在记录库）。

```ts
interface EngineDeps {
  store: RunStore;
  workflows: readonly WorkflowDefinition<any>[];
  runsDir: string; // <数据目录>/runs
  now?: () => Date; // 缺省 () => new Date()
  newRunId?: (now: Date) => string; // 缺省 newRunId
  newOwnerToken?: () => string; // 本进程的执行权令牌，缺省 crypto.randomUUID
  leaseMs?: number; // 租约时长，缺省 10 分钟
  maxRewinds?: number; // 一次推进里最多回退或重跑几次，缺省 20
}

interface RunDetail extends RunReport {
  steps: StepRecord[];
}

interface WorkflowEngine {
  start(workflowId: string, rawParams: unknown): Promise<RunReport>;
  resume(runId: string, input?: ResumeInput, options?: { force?: boolean }): Promise<RunReport>;
  cancel(runId: string, options?: { force?: boolean }): RunReport;
  show(runId: string): RunDetail;
  list(filter?: { states?: readonly RunState[] }): RunRecord[];
}
```

### 执行权（租约）

同一时刻只能有一个进程推进一次运行。做法是「租约」：

- 每个引擎实例生成一个令牌（owner）。`start` 建运行时直接以 running 状态、带着租约（到期时间 = 现在 + `leaseMs`）创建。
- `resume` 用 `acquireRun` 取得执行权；取不到就报错，什么都不改。
- 推进中，每一步开始前和结束后都调 `renewLease` 续约；步骤自己耗时长时调 `ctx.heartbeat()` 续约。续约返回 false（被接管了）时立即抛 `RUN_STATE_CONFLICT`（「执行权已被别的进程接管，本进程停止」），不再写任何记录。
- 停下时用 `releaseRun` 交还：等待中、失败、完成都通过它改状态，同时清空租约。
- 租约过期说明上次的进程异常退出或卡死，只有带 `force` 才能接管（作者确认过），接管同样走 `acquireRun`（`takeOverExpired: true`），两个进程同时接管也只有一个能成功。

### 构造时检查

`createWorkflowEngine` 时检查每个工作流：编号不重复；步骤编号在工作流内不重复，且符合 `^[a-z][a-z0-9-]*$`（要拿来当目录名）。不符合抛 `LeafPressError("INTERNAL")`。

### 运行编号

`newRunId(now)` 返回 `YYYYMMDD-HHmmss-xxxx`：日期时间取本地时间，`xxxx` 是 4 位小写字母或数字的随机串，比如 `20261005-201530-k3x9`。

### start

1. 找工作流，找不到抛 `WORKFLOW_UNKNOWN`。
2. `params = parseParams(rawParams)`，不合法时它自己抛 `USAGE`，原样往外抛。
3. 生成编号，建运行目录 `<runsDir>/<runId>`。
4. `store.createRun`：状态 running、游标 0、带上本进程的租约；每个步骤一条记录，状态 pending、`attempts` 0、`inputHashes` 为 `{}`。
5. 进入「推进」。

### resume

1. 读运行，不存在抛 `RUN_NOT_FOUND`；已完成或已取消抛 `RUN_STATE_CONFLICT`（「这次运行已经结束」）。
2. **定义比对**：记录里的步骤编号（按序号）必须和当前工作流定义的步骤编号逐个相同，否则抛 `RUN_STATE_CONFLICT`（「工作流定义已经变了，这次运行没法恢复，请取消后重新开始」）。这一步只读，不改任何东西。
3. **取得执行权**：`acquireRun(runId, { from: ["waiting", "failed"], owner, leaseExpiresAt, now, takeOverExpired: force === true, patch: { error: null } })`。返回 false 时按当前状态给出不同说明后抛 `RUN_STATE_CONFLICT`：运行中且租约没过期 →「正在别处运行」；运行中且租约已过期、没带 force →「上次似乎异常退出，确认后加 --force 接管」；其他 →「状态已经变了，请重新查看」。
4. **对齐游标**：如果游标处的步骤已经是 done，把游标前移到第一个不是 done 的步骤（防御上次在「完成这步」和「推进游标」之间退出的情况）。
5. **作废检查**：按序号检查游标之前所有 done 的步骤，以及游标处正在等待的步骤：对它 `inputHashes` 里记的每个路径重新算哈希（`sha256File`，缺失为 `"absent"`），有一个对不上，就把这一步和它后面的所有步骤重置（见「重置」），游标设到这一步。
6. 如果游标处的步骤仍是等待中（没被第 5 步重置），这次执行它时把 `input` 作为 `ctx.resume` 传入，并且沿用它原来的快照和步骤目录；其他情况一律当作「重新执行」。
7. 进入「推进」。

### 推进（start 和 resume 共用）

循环，直到游标越过最后一步或遇到停下的情况：

1. 续约（失败即停止，见上）。
2. 取游标处的步骤定义和记录。
3. **重新执行时清理步骤目录**：如果是重新执行（不是恢复等待中的步骤），而且步骤目录 `<runDir>/<stepId>` 已存在且非空，先把它改名为 `<stepId>.old-<attempts>`（已有同名就再加序号），再建一个空目录。这样旧的任务文件、旧的 AI 结果不会被新一次执行误用。
4. **拍快照**：重新执行时，调 `inputFiles(ctx)` 并逐个算哈希，作为这一步的快照；恢复等待中的步骤时沿用原快照。
5. `updateStep`：状态 running，`attempts` 加 1，`startedAt` 为当前时间，写入快照，清空 error 和 wait。
6. 组装 `ctx`：`outputs` 只包含状态为 done 的步骤的输出（按步骤编号）；`resume` 只在上面第 6 条的情况下有；`heartbeat` 为续约。
7. 执行 `run(ctx)`；它抛出的异常转成「失败」，错误文字是 `LeafPressError` 的 message，其他异常为「内部错误：」加异常的 message，不带调用栈。续约失败抛出的 `RUN_STATE_CONFLICT` 例外：直接往外抛，不写记录。
8. 按结果处理：

| 结果 | 处理 |
|---|---|
| done | 重新算快照里每个路径的哈希：和快照一致 → `completeStep`（状态 done、outputs 缺省 `{}`、`finishedAt`，游标加 1）；不一致（执行期间输入被改了）→ 这一步按「重置」处理后重新执行，计入回退次数 |
| wait | `updateStep` 为 waiting 并写入 wait；`releaseRun(owner, "waiting", { cursor })`；返回报告 |
| fail | `updateStep` 为 failed 并写入 error、`finishedAt`；`releaseRun(owner, "failed", { error })`；返回报告 |
| rewind | 目标步骤必须存在且序号不大于当前，否则按失败处理（「回退目标无效」）；回退次数加 1，超过 `maxRewinds` 按失败处理（「回退次数过多，可能陷入循环」）；把目标到当前的所有步骤重置，游标设为目标（`updateRun`），继续循环 |

9. 全部完成：`releaseRun(owner, "completed", { error: null })`，返回报告。

推进过程中记录库自己抛出的错误不拦截，直接往外抛（运行停在 running，租约过期后可以用 force 接管）。

**重置**一个步骤：状态 pending，清空 outputs、wait、error、startedAt、finishedAt、inputHashes，保留 attempts。步骤目录不在这时动，等它重新执行时按第 3 条改名。

### cancel、show、list

- `cancel(runId, { force })`：等待中或失败的运行用 `transitionRun(runId, ["waiting", "failed"], "cancelled")`。运行中的运行：租约已过期且带 force 时，先 `acquireRun`（`takeOverExpired: true`）取得执行权，再 `releaseRun(owner, "cancelled")`；否则抛 `RUN_STATE_CONFLICT`（「正在运行，不能取消；如果确定上次异常退出，等租约过期后加 --force」）。正在执行中的步骤没法从外部打断，这是有意的限制。运行不存在抛 `RUN_NOT_FOUND`，已结束抛 `RUN_STATE_CONFLICT`。
- `show`：报告加全部步骤记录；不存在抛 `RUN_NOT_FOUND`。
- `list`：直接转给 `store.listRuns`。

### 报告

`RunReport` 的 `currentStep` 和 `wait`：等待中时是游标处的步骤和它的等待请求；失败时是失败的步骤（无 wait），并带上 error；完成、取消时都没有。

### 内存存储 `createMemoryRunStore(options?)`

完全照 `RunStore` 的注释实现：读回的是深拷贝（外部改了不影响存储内容）；空值是「字段不存在」；所有标「原子」的方法同步完成判断和修改；修改时刷新 `updatedAt`（`options.now` 可注入，缺省真实时间）。

## 关键决策

1. 引擎只认 `RunStore` 接口，内存和 SQLite 两种实现跑同一套约定测试，引擎的单测不依赖数据库。
2. 执行权用租约：长步骤（以后上传大视频）靠续约保持，不会被误判成卡死；两个进程同时接管也只有一个成功。
3. 快照在步骤开始执行前拍，结束时再核对：AI 改写期间原稿被改了，改写结果不会被当成基于新稿。
4. 重新执行前把旧步骤目录改名保留：既不会误用旧结果，出了问题也能翻看。
5. 恢复前比对工作流定义：代码升级改了步骤顺序时，宁可让作者重来，也不在错位的步骤上继续跑。
6. 回退次数只在一次推进内计数：跨越多次恢复的回退都经过作者，不会无人值守地死循环。

## 验证方式

单测放在 `tests/workflows/`，用内存存储和临时目录，时间、运行编号、令牌都注入。用测试里自定义的小工作流覆盖：

1. 全是代码步骤：一次跑完，后一步能拿到前一步的输出，步骤目录都已建好，运行最终没有租约。
2. AI 步骤：先停下（状态 waiting、报告带任务文件路径、租约已清空）；恢复后这一步拿到 `ctx.resume`，完成后继续。
3. 确认步骤：同意则继续；驳回时步骤返回 rewind 回到前面某一步，从那一步重跑。
4. 失败：报告带错误；恢复时重跑失败的那一步，`attempts` 变成 2，成功后完成。步骤抛异常同样按失败处理，错误文字里没有调用栈。
5. 作废：A 步骤写出文件，B 步骤把它列为输入，C 步骤停下；改动这个文件后恢复，B 被重置并重跑、C 再次停下；文件被删掉也算改动。
6. 等待期间输入被改：B 是 AI 步骤、以 A 的产出为输入并停下；改动 A 的产出后恢复，B 当作重新执行（拿不到 `ctx.resume`），旧步骤目录被改名保留。
7. 执行期间输入被改：步骤在 run 里改动自己的输入文件，结束时被发现并重新执行；反复如此时触发回退上限而失败。
8. 恢复已完成、已取消的运行抛 `RUN_STATE_CONFLICT`；租约没过期的运行中运行，带不带 force 都抛错；租约过期后不带 force 抛错，带 force 则接管成功。
9. **并发**：对同一个等待中的运行同时发起两次恢复（`Promise.allSettled`），恰好一个成功、一个抛 `RUN_STATE_CONFLICT`；对同一个租约已过期的运行同时发起两次带 force 的恢复，同样恰好一个成功。
10. 续约：步骤里调 `ctx.heartbeat()` 会延长租约；在步骤执行期间让别的令牌接管（直接调存储的 `acquireRun`），原进程的下一次续约抛 `RUN_STATE_CONFLICT`，并且不再写入任何步骤记录。
11. 游标对齐：手工把游标处的步骤标成 done 再恢复，这一步不会被再执行一次。
12. 定义变化：等待中的运行，换一个步骤顺序不同的同名工作流定义去恢复，抛 `RUN_STATE_CONFLICT` 且运行状态不变。
13. 取消：等待中、失败的可以取消；租约有效的运行中不能取消；租约过期加 force 可以取消；已完成的不行；取消后不能恢复。
14. 未知工作流、参数不合法、步骤编号重复或不合规。
15. rewind 目标无效、回退超过上限都按失败处理。
16. `newRunId` 的格式。
17. **工作流存储约定**：新建 `tests/workflows/memory-store.test.ts`，调用 `tests/contracts/run-store.contract.ts` 的 `describeRunStoreContract("内存存储", () => createMemoryRunStore())`，全部通过。约定测试文件不许改。
