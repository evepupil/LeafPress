# 灵感 · 跑灵感

> 模块定位：每天自动给作者找选题，放进灵感收件箱：代码从知乎问题、已发作品、开发记录几个来源找候选、去重、排序，AI 从候选里挑 5～10 条写清「为什么值得写、从哪个角度写」 · 对应代码：`packages/core/src/types/idea-candidate.ts`、`packages/core/src/ideas/candidates.ts`、`src/platforms/zhihu/ideas/`、`src/ideas/`、`src/store/candidates.ts`、`src/store/probes.ts`、`src/usecases/ideas-gather*.ts`、`src/cli/commands/ideas*.ts`、`skills/leafpress/ideas.md` · 所属里程碑：[M4 灵感自动化](../roadmap.md#m4-灵感自动化) · 状态：已完成（每天定时的 codeg 自动任务已建好，等作者看过第一批后打开） · 最近更新：2026-10-19
>
> 依据：作者 2026-10-19 拍板（理由是「不知道该写啥」）：
> - 来源：知乎问题、开发记录、已发作品、博客反找知乎问题；CloudMind 不做；AI 圈热点、越用越准、小红书和 B站的灵感以后做。
> - 每条带来源链接、为什么值得写、建议角度、相关作品；每天早上 5～10 条；同一个问题不进两次，删掉的不再推。
> - 拉取、去重、排序用代码，AI 只给筛出来的写理由；选题方向用现有账号档案，不另加设置项。
> - 作者授权主控按设想无人值守做完。
>
> 接口实测（2026-10-19，用作者的知乎账号，见 [知乎开放平台接口](../调研/知乎开放平台接口.md) 第 9 节）：问题推荐只给标题和链接；问题回答摘要不给回答总数；热榜全是社会新闻；拿博客标题当主题词推荐问题很准。所以「值不值得答」代码只能按怎么找到的粗排，细的交给 AI 看已有回答的摘要来判断。

## 职责与边界

- **管**：
  - 从四个来源找候选：知乎问题（个性化推荐、按主题推荐、按博客标题反找、热榜里命中主题词的）、已发作品里数据好的、作者各项目最近的开发记录；
  - 候选去重和候选池（同一个问题、作品、项目的同一周只有一条，状态在这一条上变）；
  - 给问题补已有回答的摘要、粗排；
  - AI 挑中后变成灵感，没挑中的跳过，作者删掉的不再推；
  - 跑灵感的做法（skill）和每天定时（codeg 自动任务）。
- **不管**：
  - 写回答本身：灵感转成知乎作品后，按问题链接自动配「回答问题」工作流（[平台适配 · 知乎](平台适配-知乎.md)），这里不动；
  - 网页：灵感照原样在灵感看板里显示，删除时顺带标「不要」在后端做；
  - CloudMind、AI 圈热点、小红书和 B站的灵感。

## 结构与数据流

```
codeg 自动任务（每天 07:30，起一个 agent，照 skills/leafpress/ideas.md 做）
  ① 读知乎账号档案，提炼 3～5 个主题词
  ② leafpress ideas gather --topics <主题词> --json          ← 代码：找候选、去重、补摘要、排序
        ├─ 知乎找问题工具（src/platforms/zhihu/ideas/）：个性化推荐、主题推荐、博客反找、热榜、补回答摘要
        ├─ 已发作品：数据页的作品排行，近 7 天增长、累计主数据
        └─ 开发记录（src/ideas/devlog.ts）：C:\code 下各项目近 7 天的提交和进度流水
        → 一个写事务里合并进候选池（idea_candidates），每类只留前几名
  ③ agent 读候选池，挑 5～10 条，每条写标题、来源、为什么值得写、建议角度、相关作品
  ④ leafpress ideas add --stdin（每条带 candidateId）→ 进收件箱，候选标成已推
  ⑤ leafpress ideas skip <看过没挑的编号> → 标成跳过（14 天内不再进池）

作者在网页删掉一条由候选变来的灵感 → 候选标成不要，以后再也不推
灵感转知乎作品 → 详情里有问题链接 → 自动配「回答问题」工作流
```

联网只发生在 ②，而且都在事务外；联网结束后在一个写事务里重新按键读候选、合并，避免跑的过程中作者删了灵感、合并时又把它的候选翻回池里。

## 候选

类型在 `packages/core/src/types/idea-candidate.ts`（主控定，照抄）。

### 键和三类候选

| 类 | 键 | 标题 | 链接 | 挂账号 |
|---|---|---|---|---|
| question 知乎问题 | `zq:<问题编号>` | 问题标题 | `https://www.zhihu.com/question/<编号>` | 找问题用的那个知乎账号 |
| followup 已发作品续写 | `wf:<作品编号>` | 作品标题 | 作品链接 | 空（AI 判断发在哪） |
| devlog 开发记录 | `dev:<规范化的项目路径>:<ISO 周>` | 项目文件夹名 | 空 | 空 |

开发记录的键用完整路径（转小写、反斜杠换成 `/`、去掉末尾的 `/`，例如 `dev:c:/code/leafpress:2026-W43`）：两个根下有同名项目时不会撞成一条。

同一个问题不管是推荐来的、热榜来的还是博客反找来的，键都一样，合并成一条（`via`、`topics`、`blogWorkIds` 取并集）。开发记录按周：同一个项目一周最多推一次，下一周是新键。

### 状态

```
找到 ──► new（在池里）──AI 挑中──► suggested（已推，记下灵感编号）──作者删掉灵感──► rejected（不要）
             │
             └──AI 看过没挑──► skipped（跳过）──14 天后再被找到──► new
```

- **挡住不再进池**（`isBlocked`）：suggested、rejected 永远挡；skipped 从跳过那刻（`updatedAt`）起 14 天内挡。
- 已经是 new 的候选再被找到：刷新内容和分数，状态不变。
- **池的上限**：问题 20 条（四种找法分组轮流取，见 `pickQuestions`），续写 3 条，开发记录 5 条。挤不进池的不留：这次新找到的不入库，原来在池里的删掉。它们 AI 没看过，不进冷却，下次找到时再比。

## 来源

### 知乎问题（`src/platforms/zhihu/ideas/`）

平台层新增「找问题工具」`QuestionFinder`，接口在 `src/platforms/types.ts`（主控定）；登记表 `questionFinder("zhihu")` 给它，其余平台给 `undefined`。客户端复用 `createZhihuClient`（鉴权、1.1 秒间隔、重试、额度用完的报错都现成）。

**四个接口**（`api.ts`，每个一个函数，只做请求和解析，返回干净的结构）：

| 函数 | 请求 | 解析 |
|---|---|---|
| `recommendQuestions(client, { query?, count })` | `GET /user/question_recommendations`，`Count` 1～20；`Query` 只在给了时才带（不传是按账号画像，传空串会报错） | `Data.Items[]` 的 `Title`、`Url`；`Url` 认不出问题编号的丢掉 |
| `answerSummaries(client, questionUrl, limit)` | `GET /content/question_answers`，`QuestionUrl`、`Limit` | `Data.Items[].Summary`，压掉多余空白，每条截到 200 字，空的丢掉 |
| `hotQuestions(client)` | `GET /content/hot_list`，`Limit` 30 | 只留 `Url` 是问题的（实测 30 条全是问题，链接带 `utm_` 参数） |
| `searchQuestions(client, query)` | `GET /content/zhihu_search`，`Query`、`Count` 10 | 只留 `ContentType` 是 answer 或 question（不分大小写）、`Url` 里能取出问题编号的；标题去掉 `<em>` 标签和末尾的「 - 知乎」；实测结果大多是文章，问题很少 |

问题编号统一用 core 的 `questionIdOf(url)` 取：认 `zhihu.com/question/<数字>`（带不带 `www`、后面跟不跟 `/answer/…`、查询串、`#` 都认），链接一律规范成 `https://www.zhihu.com/question/<编号>`。

**`createZhihuQuestionFinder().find(ctx)` 的步骤**（每步各自 try/catch，一步出错只记在它的 `warning` 里，接着做下一步）：

1. 取密钥 `ctx.secret("access-secret")`；没有就 `{ ok: false, reason: "知乎账号还没填开放平台密钥", fixHint: "在接入里填上开放平台的 Access Secret" }`。
2. **personal**：`recommendQuestions({ count: 20 })`。
3. **topic**：每个主题词 `recommendQuestions({ query: 主题词, count: 10 })`，记下命中的主题词。
4. **blog**：每篇博客 `recommendQuestions({ query: 博客标题, count: 5 })`，再 `searchQuestions(博客标题)`，记下博客作品编号。推荐来的和搜索来的都要过一关：问题标题和这篇博客的标题按 `relatedWorkIds` 的规则算得上相关才要。真实数据里两条路都会跑偏：讲 Git Bash 中文乱码的博客，推荐出了「为什么中国文化进步很慢」「英语学习时发现抛不开中文怎么办？」，搜索也带出过同类。
5. **hot**：只在有主题词时跑；`hotQuestions()` 里标题包含任一主题词的（不分大小写）才要，记下命中的主题词。
6. 按问题编号合并，去掉 `ctx.skipQuestionIds` 里的；`via` 按 personal、topic、blog、hot 排。
7. 返回 `{ ok: true, questions, stages }`，`stages` 依次是 personal、topic、blog、hot，各带找到的条数和警告；`find` 不补摘要。

**`summarize(ctx, questions)`**：补摘要单独一个方法，由用例在定好进池的问题之后调（原来在 `find` 里按自己的粗排补，和最后进池的对不上，真实数据里 20 个进池问题只有 7 个带摘要）。按给的顺序每个 `answerSummaries(url, 3)`；当天额度用完就停，记 warning「今天问题发现的额度用完了，只补了 N 个」；每秒超限耗尽或单个问题出错跳过它接着补，记 warning；密钥失效 `{ ok: false, …, expiredKey: "access-secret" }`。

**出错**：

- `ZhihuAuthenticationError`（密钥失效）：整个 `find` 返回 `{ ok: false, reason, fixHint, expiredKey: "access-secret" }`，用例照拿数据的做法把密钥标成过期；
- 额度用完（`ZhihuApiError` 的 `code === 30001`）：这一步记警告，后面同一额度组的步骤（personal、topic、blog 里的推荐、summary）直接跳过并记「今天问题发现的额度用完了」；热榜和搜索是别的额度，照跑；
- 其余错误：这一步记警告，接着做。

**额度**（实测额度接口）：问题发现组每天 100 次，一次跑灵感最多用 1 + 5 + 3 + 20 = 29 次；热榜每天 100 次，用 1 次；搜索每天 5000 次，用 3 次。

### 博客反找问题

用例挑博客作品：博客账号里状态已完成、有链接、标题非空的作品，30 天内拿去反找过的跳过（`idea_probes` 记 `blog:<作品编号>` 的时间）；从没找过的在前，再按发布日期新的在前，取 3 篇。找问题工具的 blog 一步没出警告时，这几篇记上这次的时间。

### 已发作品续写

用数据页同一份数据（`MetricsInput`）和作品排行 `topWorks`：

1. 符合条件的作品：已完成、有链接、发布日期早于 7 天前（没写发布日期的也算）、`wf:<作品编号>` 没被挡住、近 7 天增长大于 0；
2. 按近 7 天增长取前 3 个。不按累计数据补：真实数据里补进来的是最近一个阅读都没有的老回答，续写没有意义；
3. payload 照类型填：`interactions` 在第二个数不是互动的平台（博客）写 null。

### 开发记录（`src/ideas/devlog.ts`）

接口在 `src/ideas/types.ts`（主控定）。`readDevActivity({ roots, since, exec })`：

- 在每个根文件夹下面一层找项目：有 `.git`（文件夹或文件都算，工作树是文件）的才算；根不存在就跳过；
- 提交：`git -C <项目> log --since=<since>T00:00:00+08:00 --no-merges --pretty=format:%s -n 30`，超时 15 秒；失败当没有提交，进度流水照读；
- 进度流水：`<项目>/docs/进度/` 下文件名是 `YYYY-MM-DD.md`、日期不早于 since 的，新的在前取 10 个；读二级标题（「## 」开头、不是「### 」的行，去掉井号和首尾空白）；
- 有提交或有进度流水的项目才返回，按提交条数从多到少，再按项目名。

用例：根文件夹取配置 `ideas.devRoots`（字符串数组，可选）；没配时 Windows 上 `C:\code` 存在就用它，否则不跑这个来源。时间窗是今天往前 7 天（含今天）。取前 5 个项目，键里的周用今天的 ISO 周。

配置：`src/config/schema.ts` 的 `ConfigSchema` 加 `ideas: z.strictObject({ devRoots: z.array(非空字符串).optional() }).default({})`；旧配置文件没有这一项照样能读（缺省 `{}`），配了非法值照现有规矩报配置错误。

## 打分和候选池（`packages/core/src/ideas/candidates.ts`，纯函数）

| 函数 | 规则 |
|---|---|
| `questionKey(id)`、`followupKey(workId)`、`devlogKey(path, week)` | 见上面的键；`devlogKey` 自己规范化路径 |
| `questionIdOf(url)` | 见知乎问题一节；认不出返回 undefined |
| `titleKey(title)` | 比标题用：转小写，去掉末尾「 - 知乎」，去掉所有空白和标点（中英文标点、引号、括号、问号都算）；剩下空串时返回空串 |
| `questionIdsIn(text)` | 文字里出现的所有知乎问题编号（`zhihu.com/question/<数字>`），去重，按出现先后 |
| `isoWeek(day)` | ISO 8601 周，形如 `2026-W43`（周一开始，跨年按 ISO 规则，例如 2026-12-31 是 `2026-W53`，2027-01-01 也是 `2026-W53`） |
| `isBlocked(candidate, now)` | 见状态一节；`candidate` 为 undefined 时 false |
| `scoreQuestion({ via, relatedWorkIds })` | `via` 里最高的权重（blog 30、topic 20、personal 15、hot 10）+ 每多一种找法加 5 + 有相关作品加 10 |
| `scoreFollowup(payload)` | 近 7 天增长 + 累计主数据 ÷ 1000000（增长为主，累计只用来分先后） |
| `scoreDevlog(payload)` | 提交条数 + 进度流水文件数 × 3 |
| `relatedWorkIds(title, works, limit = 3)` | 标题切词：转小写，去掉标点和空白；连续的英文数字算一个词（2 个字以上），汉字取相邻两字；**去掉通用词**（`GENERIC_BIGRAMS`）；两边去重后的词，交集 ÷ 较少一边的词数 ≥ 0.2，且交集至少 2 个词，才算相关；按相似度从高到低、再按作品编号，最多 3 个 |
| `primaryVia(via)` | `via` 里权重最高的那个（blog 30、topic 20、personal 15、hot 10）；空数组返回 undefined |
| `pickQuestions(items, limit)` | 进池和补摘要共用：按 `primaryVia` 分成 personal、topic、blog、hot 四组，组内按 score 从高到低、再按输入的先后；然后按 personal、topic、blog、hot 的顺序轮流各取一个，某组取完就跳过，直到取满 `limit` 或全取完；返回取中的，顺序就是取的顺序。真实数据里按分数一刀切，个性化推荐的 20 个问题一个都没进池 |
| `trimPool(pool)` | 只看 new 的；问题用 `pickQuestions(问题, 20)`；续写、开发记录各按 score 从高到低、再按 updatedAt 新的在前、再按 id，续写留 3、开发记录留 5；返回 `{ keep, overflow }` |
| `sortCandidates(list)` | 类按问题、续写、开发记录；类里按 score 从高到低，再按 id |

常量写在同一个文件：`SKIP_COOLDOWN_DAYS = 14`、`POOL_LIMITS = { question: 20, followup: 3, devlog: 5 }`、`VIA_WEIGHTS`、`GENERIC_BIGRAMS`。

`GENERIC_BIGRAMS`（问句里的通用说法，算相似时不算数；真实数据里「有哪些」「推荐」让一堆不相干的问题都关联到同两篇作品）：如何、何看、看待、怎么、怎样、为什、什么、有哪、哪些、推荐、可以、是否、应该、评价、一个、这个、那个、我们、你们、他们、自己、没有、有没、现在、一些、的人、大家、觉得、知道、问题、方法、时候、能不、不能、是不、不是、还是、真的、为何、有什、么样、样的、的是、是什。

## 用例（`src/usecases/ideas-gather.ts`，改 `src/usecases/ideas.ts`）

接口在 `packages/core/src/api/usecases.ts`（主控定）。

**`gatherIdeas({ topics, onProgress })`**：

1. 主题词：去首尾空白、去空、去重，超过 5 个报 USAGE「主题词最多 5 个」。
2. 读全部账号、作品、灵感、候选。要跳过的问题编号：
   - 知乎账号作品链接里的问题编号（链接带 `/question/<编号>` 的）；
   - 灵感的 `text`、`detail`、`sourceDetail`，作品的 `title`、`brief` 里出现的问题编号；
   - 被挡住的 `zq:` 候选的问题编号。

   另外按标题挡：作者知乎作品的 `titleKey` 集合。导入的回答链接是 `/answer/<编号>`，不带问题编号，但回答作品的标题就是问题标题；候选问题的 `titleKey` 落在这个集合里的不进池（空串不算）。
3. **知乎问题**：只用一个知乎账号找：多个知乎账号时取编号排序最小的那个（几个账号共用开放平台额度，按账号各跑一次会把额度翻倍）。博客按上一节挑。`{ ok: false }` 时记一条来源警告「知乎问题：<原因>」；有 `expiredKey` 照拿数据的做法标过期。
4. **已发作品**、**开发记录**：按上一节。
5. **补回答摘要**（联网，仍在事务外）：先在内存里按合并的规则算一遍（读出的候选加这次找到的，去掉被挡的和按标题挡的），用 `pickQuestions(问题, 20)` 定出会进池的问题；其中还没有摘要的（新找到的，或池里原有但摘要为空的），按 `pickQuestions` 的顺序交给找问题工具的 `summarize`，最多 20 个。拿回来的摘要在合并时写进对应问题的 payload。来源报告「补回答摘要」写补上了几个、警告。
6. **合并**（一个写事务里，重新按键读）：
   - 键不存在：插入，编号 `c-<序号>`（`meta.nextSerial("candidate")`），状态 new；
   - 键存在且是 new，或是 skipped 且冷却已过：更新内容和分数，状态 new（skipped 回到 new 的算新进池）；
   - 键存在且被挡住：不动；
   - 问题标题的 `titleKey` 等于作者知乎作品标题的：不进池；
   - 键存在时账号不改（第一次进池时挂的账号）；
   - 问题的 `relatedWorkIds` 用 `relatedWorkIds(标题, 全部作品)` 算，分数用 `scoreQuestion`；
   - 合并完 `trimPool`，overflow 删掉（`candidates.remove`）：这次新插的不留，原来在池里的也删；它们 AI 没看过，不进冷却；
   - 博客反找时间写进 `idea_probes`。
7. 返回 `GatherReport`：来源依次是「知乎个性化推荐」「知乎主题推荐」「博客反找问题」「知乎热榜」「补回答摘要」「已发作品」「开发记录」，各带找到几条、新进池几条、警告；没有知乎账号时知乎几项合成一条「知乎问题」，警告「还没有知乎账号」；没有主题词时主题推荐和热榜的警告写「没给主题词，跳过」。`pool` 是合并后所有 new 的候选（`sortCandidates`）。
8. `onProgress` 报每一步（「知乎：个性化推荐…」「已发作品…」），命令行打到标准错误。

**`addIdeas`**（改）：带 `candidateId` 的，先在事务里检查：候选存在、状态 new、这一批里不重复；不满足整批不加，报 USAGE 并逐条说明（「候选 c-3 已经推过」「候选 c-9 不存在」）。没给 `accountId` 用候选的；没给 `sourceDetail` 用候选的链接（开发记录用项目路径）。加完候选标成 suggested，记下灵感编号。

**`deleteIdea`**（改）：同一个事务里，`candidates.getByIdea(id)` 找到且是 suggested 的标成 rejected，再删灵感。

**`skipCandidates(ids | "rest")`**：编号都得是 new，否则报 USAGE；`"rest"` 是池里全部 new 的。返回标过的候选。

**`listCandidates({ state })`**：缺省只要 new；`sortCandidates`。

依赖注入：用例工厂多两个可注入项，`readDevActivity`（缺省用 `src/ideas/devlog.ts`）和 `devRoots`（缺省按配置和上面的规则）；时间、`fetch`、`sleep`、`exec` 照现有写法注入。

## 记录库（第 3 版升级）

```sql
CREATE TABLE idea_candidates (
  id TEXT PRIMARY KEY,
  key TEXT NOT NULL UNIQUE,
  kind TEXT NOT NULL,
  title TEXT NOT NULL,
  url TEXT,
  account_id TEXT REFERENCES accounts(id) ON DELETE SET NULL,
  score REAL NOT NULL,
  state TEXT NOT NULL,
  idea_id TEXT,
  payload TEXT NOT NULL,
  first_seen_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
CREATE INDEX idea_candidates_state ON idea_candidates(state);
CREATE UNIQUE INDEX idea_candidates_idea ON idea_candidates(idea_id) WHERE idea_id IS NOT NULL;
CREATE TABLE idea_probes (
  key TEXT PRIMARY KEY,
  at TEXT NOT NULL
);
INSERT INTO meta (key, value) VALUES ('serial_candidate', 0);
```

- `idea_id` 不加外键：灵感删了，候选还要记着它是从哪条灵感变来的（rejected）；但加部分唯一索引，同一条灵感只能对应一个候选，撞了抛 STORE_FAILED。
- 仓库接口 `IdeaCandidatesRepo`、`IdeaProbesRepo` 在 `src/store/types.ts`（主控定）；写都走 `writeRepo`（自动加变更序号），读多张表时照现有规矩包读事务；`payload` 存 JSON，读回时校验 `kind` 和行的 `kind` 一致，坏了抛 STORE_FAILED。
- 升级照现有机制：先备份再升；作者的真实数据目录在第一次用新版本打开时自动升到第 3 版。

## 命令行（`src/cli/commands/ideas.ts`）

| 命令 | 用例 | 给人看的输出 | `--json` |
|---|---|---|---|
| `ideas gather [--topics <词,词>]` | `gatherIdeas` | 先逐个来源一行「知乎主题推荐：找到 30 条，新进池 18 条」（有警告接在后面）；再列候选池 | `{ ok, sources, pool }` |

`--rest` 是池里此刻全部 new 的，给作者手动清池用；agent 跑灵感时一律给编号，只跳过自己看过的（跑的过程中另一次 gather 新进池的不会被误跳）。
| `ideas add --stdin`（改） | `addIdeas` | 同原来 | 同原来 |

- `ideas add --stdin` 的每项多认 `candidateId`。
- 候选池的显示：分「问题」「续写」「开发记录」三段，每条第一行「编号  标题」，下面缩进写：
  - 问题：怎么找到的（「个性化推荐 · 主题：大模型 · 博客反找：b-3」）、链接、相关作品编号、第一条回答摘要截 60 字；
  - 续写：「<平台> · 近 7 天 +<增长> · 累计 <主数据>」、链接；
  - 开发记录：「本周 <n> 次提交、<m> 份进度流水」、最近 3 条提交说明。
- 进度打到标准错误；有警告不算失败，退出码 0。
- `--topics` 用逗号分隔（中英文逗号都认）。

## 跑灵感的做法和每天定时

- **做法**写在 `skills/leafpress/ideas.md`（主控写），`SKILL.md` 里加一节指过去，说「跑灵感」时照做：读知乎账号档案提炼主题词 → `ideas gather` → 挑 5～10 条（问题至少 3 条、续写和开发记录各不超过 2 条，跑题的不要）→ 按固定格式写灵感 → `ideas add --stdin` → `ideas skip <看过没挑的编号>`。
- **灵感的格式**：`text` 是一句话标题（问题就用问题标题）；`detail` 固定四行：
  ```
  来源：<链接或位置>（<怎么找到的>）
  为什么值得写：<一两句，具体>
  建议角度：<一两句，具体到写什么>
  相关作品：<编号《标题》，没有写「无」>
  ```
  知乎问题挂知乎账号，来源 `schedule`；开发记录来源 `devlog`；续写来源 `schedule`。转作品时 `detail` 就是作品的要求，问题链接在里面，自动配回答工作流。
- **每天定时**：codeg 自动任务「LeafPress 跑灵感」，每天 07:30（06:00 拉完数据之后），提示词自带全部路径和步骤（自动任务看不到对话）。

## 关键决策

1. **代码找、AI 挑**：拉取、去重、排序、补摘要都是代码，确定、可测、不花 AI 额度；AI 只看 30 条以内的候选，写 5～10 条理由。
2. **主题词由 AI 每次从档案提炼、当参数传给代码**：作者说不另加设置项；档案是自由写的，代码读不懂，AI 读得懂。
3. **候选池加状态**：「不重复推」「删了不再推」「没挑中的过一阵再看」都落在一张表的状态上，一个键一行。
4. **知乎只用官方开放平台**：合规、不爬网页；问题发现每天 100 次额度，一次最多用 29 次。
5. **博客反找用博客标题直接当主题词**：实测比短关键词准（「claude code里面使用chatgpt的模型教程」推回来 8 个 Claude Code 问题，「黑苹果 硬件」推回来的是泛泛的硬件问题）。
6. **开发记录只读本机**：git 提交和进度流水，不联网；按周一个候选，一周最多推一次。
7. **定时用 codeg 自动任务**：要 AI 判断的定时活用 AI 工具自带的定时任务（架构设计 ⑪），codeg 能在本机按时间起无人值守的 agent 会话。
