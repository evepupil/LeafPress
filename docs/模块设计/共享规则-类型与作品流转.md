# 共享规则 · 类型与作品流转

> 模块定位：领域类型、平台和工作流目录、作品和灵感怎么变（纯函数），命令行、本机服务、网页共用一份 · 对应代码：`packages/core/src/`（types、catalog、api、dates、format、labels、workflows、works、ideas） · 所属里程碑：[M1 底座](../roadmap.md#m1-底座)、[M3 知乎](../roadmap.md#m3-知乎) · 状态：已完成 · 最近更新：2026-10-10
>
> 同层的另一份：[共享规则 · 接入与数据统计](共享规则-接入与数据统计.md)。规则来源：网页原型 `web/src/lib/work-engine.ts`、`board.ts`、`web/src/data/clock.ts`、`format.ts`、`labels.ts`，搬过来后去掉对演示数据和演示时刻的依赖。

## 职责与边界

- 管：所有领域类型；平台目录和工作流目录；作品状态怎么变（接手、做完一步、代码步骤的结果、退回、交还、反馈、拖动、改字段）；看板排序和挑下一个；转作品；任务说明文字；灵感排序和挪列；日期计算；数字和时间的显示格式；中文标签。
- 不管：读写文件、记录库、联网、拿当前时间。时间、编号、排序位置都由调用方传进来，所以同样的输入永远得到同样的结果。
- 改作品状态的规则只有这一份：本机服务（网页的操作）和命令行（agent 的操作）都经用例调这里。

### 时间约定

- `IsoTime` 是带本地时区偏移的时间（`2026-10-08T09:30:00+08:00`，到秒）。`dayOf(time)` 直接取前 10 个字符，所以永远是本地日期。
- 规则函数要用时间的都从参数拿：改作品的函数收 `at: IsoTime`，发布日期取 `dayOf(at)`。

### works/engine：作品状态怎么变

结果类型：

```ts
export type RuleFailure = { ok: false; code: "STATE_CONFLICT" | "INVALID"; reason: string }
export type WorkResult = { ok: true; work: Work } | RuleFailure

// CodeOutcome（代码步骤的结果）已由主控写在 types/work.ts，这里直接用
export const GENERIC_ASK = "你把它挪到了这里。看完在下面写反馈，agent 会照着接着做。"
```

所有函数都不改传进来的对象，返回新对象。改了作品就把 `updatedAt` 设成 `at`，按下表追加记录（`log` 末尾加 `{ at, text }`）。失败时 `reason` 是给人看的中文，说清为什么不行、该怎么办。

查询：

```ts
export function stepState(work: Work, index: number): StepState   // 规则同原型：done 或 index < step 为 done；index > step 为 pending；当前步：进行中 running、等你处理 waiting、待实现 pending
export function currentStep(work: Work, workflow: WorkflowDef): WorkflowStep | undefined  // 已完成或越界时 undefined
export function progressText(work: Work, workflow: WorkflowDef): string  // 「第 2/3 步 · 你去发布」；已完成「3/3 步」
export function waitingLabel(work: Work, workflow: WorkflowDef): string  // 当前步骤要你动手就用步骤名，否则「你来看一下」
export function askFor(work: Work, workflow: WorkflowDef, vars: StepVars): string  // 当前步骤的 ask 填好占位符；没有就是 GENERIC_ASK
export function extractUrl(text: string): string | undefined  // 正则同原型：取第一个 http(s) 网址，遇到空白和中文标点、右括号截止
```

内部的两个公共动作（不导出，下面的函数都用它们）：

- **往下走一步（advance）**：`step` 加一，记录「完成：<这一步的名字>」，清掉 `error`。
  - 走完了（`step` 等于步骤数）→ 完成（见下）。
  - 下一步要你动手 → toWaiting（`ask` = 下一步的 ask 填好占位符，没写就 GENERIC_ASK），记录「等你：<下一步的名字>」。注意：从要你动手的步骤走到代码步骤时 `feedback` 保留（归档链接要从里面取链接），直到下一次进入等你处理才清掉。
  - 其余 → 进行中，清掉 `ask`，`lease` 保留。
- **进入等你处理（toWaiting）**：状态等你处理，`ask` = 传入的话，清掉 `lease`、`error` 和 `feedback`（上一轮的反馈已经在 `feedbackHistory` 里；清掉是为了作者下一次写的反馈不会和旧的混在一起，agent 接手时也不会把旧反馈当成这一轮的）。所有变成等你处理的路径都走它：advance 到要你动手的步骤、`startWork` 时要你动手但没反馈、代码步骤要你处理、退回到要你动手的步骤、拖到等你处理。
- **完成（complete）**：状态已完成，`step` = 步骤数，清掉 `ask`、`lease`、`error`；`publishedAt` 没有就设成 `dayOf(at)`；`url` 没有就从 `feedback` 里取。记录「已发布，链接已归档：<url>」，没有链接时「已完成，还没有链接」。

改状态的函数：

| 函数 | 前提（不满足返回 STATE_CONFLICT） | 结果 |
|---|---|---|
| `startWork(work, workflow, { at, lease, vars, takeover? })` | 待实现；`takeover` 为真时也接受进行中（用例已判断可以接管） | 当前步骤要你动手且有 `feedback`：记录「读了你的反馈，接着做」，这一步记为完成并往下走（advance；往下走后若是进行中，挂上 `lease`）。要你动手但没有反馈：toWaiting（`ask` 用 askFor），记录「等你：<步骤名>」。其余：进行中，挂上 `lease`，清掉 `ask`，记录「agent 接手：<步骤名>」（takeover 时记录「agent 接管：<步骤名>」） |
| `completeAiStep(work, workflow, { at, vars })` | 进行中，当前步骤是 AI | advance。当前步骤是代码时 reason 写「这一步是自动步骤，用 leafpress work run」；要你动手时写「这一步要作者来做」 |
| `applyCodeResult(work, workflow, outcome, { at, vars })` | 进行中，当前步骤是代码 | done：有 url / publishedAt 就写上，记录「完成：<步骤名>」后加 note（有的话，用「：」接），再往下走（advance 里不再重复记「完成」）。ask：toWaiting（`ask` = outcome.ask），步骤不动，记录「等你：<步骤名>」（加 note）。fail：仍是进行中，`error` = outcome.error，记录「出错：<步骤名>：<error>」 |
| `backToStep(work, workflow, target, { at, vars })` | 进行中，`0 <= target < step` | `step` = target，清掉 `error`；目标是要你动手的步骤 → toWaiting（ask 用 askFor）；否则仍是进行中（`feedback` 保留，agent 照着改）。记录「退回到第 <target+1> 步：<步骤名>」 |
| `releaseWork(work, { at, order })` | 进行中 | 待实现，`order` = 传入值，清掉 `lease`，记录「agent 交还，回到待实现」 |
| `submitFeedback(work, workflow, text, { at, order })` | 等你处理；`text` 去掉首尾空白后不能为空（空返回 INVALID「反馈不能是空的」） | 待实现，`order` = 传入值（用例传最前面），`feedback` = 文字，`feedbackHistory` 追加 `{ at, step, stepName, text }`（stepName 取当前步骤名，越界为空串），清掉 `ask`，记录「你的反馈：<文字>」 |
| `moveWork(work, workflow, status, { at, order, vars })` | 已完成的不能挪出来；`status` 只能是 todo、waiting、done；挪到原来那一列原样返回 ok | 先记录「你把它挪到了「<列名>」」，原来是进行中的清掉 `lease`。待实现：`order` = 传入值，清掉 `ask`。等你处理：toWaiting（ask 用 askFor）。已完成：complete |
| `updateWork(work, patch, { at, workflow? })` | 标题去空白后不能为空（INVALID）；换工作流只能在待实现且第 0 步（否则 STATE_CONFLICT「已经开始做了，不能换工作流」），并且要传新的 `workflow` | 写上改动的字段；`url`、`question` 为 null 时清掉；换工作流时记录「换成「<名字>」工作流」 |

和原型的区别：

- 原型的 `advance` 一个函数包了「接手」和「做完一步」，这里拆成 `startWork` 和 `completeAiStep`，并且 AI 步骤要 agent 明确说「做完了」才往下走。
- 代码步骤的结果由平台适配给出（`applyCodeResult`），不再在规则里拼博客链接。
- 新增退回、交还、代码步骤出错。

## 关键决策

1. **规则只写一份，放共享包**：网页拖一张卡片和 agent 在命令行做完一步，走的是同一个函数，不会出现两边算法不一样。
2. **不碰时钟和存储**：时间、编号、排序位置都传进来；测试不用造假时钟，网页也能直接用这些函数做「先改界面再等服务端确认」。
3. **AI 步骤由 agent 明确说做完**：agent 把产出放进任务文件夹再报「做完了」，LeafPress 才往下走；代码步骤由命令行执行，结果交给规则。原型里「让 AI 做」自动一步步走的逻辑不要了。
4. **反馈后回到待实现最前面，agent 接手时把你那一步记为完成**：agent 只看待实现就能接上要继续的作品；要改的意见 agent 读到后可以退回前面的步骤重做。
5. **平台和工作流的定义是静态数据，放共享包**：网页、命令行同步就能用；代码步骤和拿数据的工具的实现放 `src/platforms/`（见 [平台适配](平台适配-登记表与通用工作流.md)）。
6. **时间一律带本地偏移**：日期直接取前 10 个字符就是本地日期，和原型的写法一致；租约到期比较用毫秒时间戳，不比字符串。

## 验证方式

单测和源文件放一起（`*.test.ts`），用小的手写样例（几个账号、几个作品），不依赖网页的演示数据。期望值写具体值。至少覆盖：

1. dates：跨月跨年加减、周一（周日算上一周）、区间、`toIsoTime` 的格式（用 `process.env.TZ = "Asia/Shanghai"` 固定时区）。
2. format：照搬原型 `format.test.ts` 的全部用例，相对时间改成传 now。
3. workflows：知乎灵感或新建的标题/brief 有问题链接时挑回答工作流；知乎博客来源挑博客改写；无问题链接挑写文章；没有 `questionPattern` 的平台不触发 question；`pickFromList` 和 `pickWorkflow` 的通用回落。
4. engine，用通用写稿走完整一遍：待实现 → 接手（进行中、挂租约、记录）→ AI 做完（停在「你去发布」、ask 里文件夹路径已填、租约清掉）→ 反馈「发布了 https://zhuanlan.zhihu.com/p/1」（回到待实现、order、历史一条）→ 接手（你那一步记为完成，当前是归档链接、进行中）→ 代码结果 done 带 url（已完成、publishedAt = dayOf(at)、记录「已发布，链接已归档：…」）。
5. engine 的前提检查：每个函数在不允许的状态下返回 STATE_CONFLICT，reason 是中文；空反馈 INVALID；已完成不能挪出来；开始后不能换工作流。
6. 代码步骤 ask：停在等你处理且步骤不动；反馈后接手 → 进行中、当前仍是这个代码步骤、feedback 还在。代码步骤 fail：仍进行中、error、记录；之后 done 清掉 error。
7. 退回：退回到 AI 步骤仍进行中、feedback 还在；退回到要你动手的步骤变等你处理且 feedback 清空，之后再接手不会跳过这一步；目标不小于当前步骤时报错。
8. 拖动：进行中挪到待实现清掉租约；挪到等你处理的 ask（要你动手的步骤用步骤的话，AI 步骤用 GENERIC_ASK）；挪到已完成从反馈取链接。
9. board：排序三种列、筛选、`reorderTodo`、`topOrder` / `bottomOrder`（空列表时分别是 0 和 1）、`pickNext` 跳过 canStart 为假的、`newWorkId`。
10. convert：一转三（三个平台）编号和 order、标题和 brief 去空白、记录文字、来源是作品时的记录文字。
11. context：按格式逐段断言（含有来源、有反馈记录两条、有出错、有文件、档案为空几种情况）；`taskState`。
12. ideas：排序、挪列、已转作品不能挪、markConverted 去重。

`packages/core` 的门禁全部通过；不许出现 `any`。
