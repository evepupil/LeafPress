## 职责与边界

- 管：博客的定义（配置项、工作流、拿数据的工具说明）；导入工具；三个代码步骤；Umami 客户端和拿数据工具。
- 不管：作品状态怎么变（共享规则）、什么时候调（用例）、写稿本身（agent 按工作流的说明写，问题复盘类用作者的「博客问题复盘」skill）。
- 只碰博客仓库里这一篇文章的文件：`content/posts/zh/<slug>.mdx`、`content/posts/en/<slug>.mdx`、`public/images/posts/<slug>/`。别的文件一律不动；检查过程中被改动的文件跑完要还原。

## 博客仓库的事实（侦察结论）

- 文章：`content/posts/{zh,en}/<slug>.mdx`，slug 就是文件名；frontmatter 必填 `title`、`description`（240 字以内）、`published`、`locale`、`tags`（至少一个、不重复），可选 `draft`、`pinned`、`updated`、`image`、`translationKey`；中英文靠 `translationKey` 配对。
- 网址：中文 `<站点>/posts/<slug>/`，英文 `<站点>/en/posts/<slug>/`；站点是 `https://blog.chaosyn.com`。
- 上线：推到 `main` 后 Cloudflare Pages 自动构建（几分钟）。Notion 同步由 GitHub Action 在线上提交，所以本地仓库可能落后，推送前要先拉最新。
- 作者的「博客问题复盘」skill 发文前跑六项检查：`content:check`、`format:check`、`lint`、`typecheck`、`test`、`build`（`content:check` 约 7.5 秒、`format:check` 约 17 秒，`build` 最久）。图片放 `public/images/posts/<slug>/`。

## 三个代码步骤（`steps/`，按 `blog-write/<步骤>` 登记）

公共：仓库 = 配置 `repo-path`，站点 = `site-url`（缺了直接 fail「博客仓库位置还没配」）。slug 读 `{folder}/slug.txt`（去空白），必须匹配 `^[a-z0-9]+(?:-[a-z0-9]+)*$`。稿子：`中文稿.mdx`、`英文稿.mdx`，图片：`images/` 下全部文件（可以没有）。目标路径：`content/posts/zh/<slug>.mdx`、`content/posts/en/<slug>.mdx`、`public/images/posts/<slug>/`。所有 git 命令带 `--no-optional-locks`（只读的）或照第一阶段 `git-run.ts` 的做法；外部命令输出写进结果前用 `redactSecrets` 抹密钥。

**跑博客检查（gate）**

1. 仓库是 git 仓库、当前分支是 `main`、没有未提交的已跟踪改动（`git status --porcelain --untracked-files=no` 为空），否则 fail（「博客仓库有没提交的改动，先处理」等，说清是哪种）。目标路径已经存在 → fail「slug 撞了已有文章：<路径>」。
2. 拉最新：落后就 `fetch` + `merge --ff-only`（沿用第一阶段的 `syncRepo`）；分叉了 → fail。
3. 记下此刻未跟踪的文件清单；把稿子和图片复制到目标路径；`pnpm exec prettier --write <目标文件>`。
4. 依次跑 `pnpm content:check`、`format:check`、`lint`、`typecheck`、`test`、`build`（每项开跑前 `heartbeat()`；超时：build 15 分钟，其余 5 分钟），第一项没过就停。
5. 把排好版的目标文件复制回任务文件夹（覆盖 `中文稿.mdx`、`英文稿.mdx`，后面的步骤用排好版的）；写 `{folder}/检查结果.txt`（每项：通过 / 没过、用时；没过的那项附最后 80 行输出）和 `{folder}/.gate.json`（`{ slug, hash, checkedAt }`，hash 是两篇稿子加全部图片内容的 sha256）。
6. **还原仓库**：删掉复制进去的目标文件；已跟踪文件一律还原到 HEAD（第 1 步保证了开跑前没有已跟踪改动，所以安全）；第 3 步之后新出现、又没被忽略的未跟踪文件删掉。不管检查过没过都要还原。
7. 全过 → `{ kind: "done", note: "博客检查全过" }`；没过 → `{ kind: "fail", error: "博客检查没过：<哪一项>（详情在 检查结果.txt）" }`（agent 改好稿子再 `work run`）。

**提交并推送（publish）**

1. `.gate.json` 不存在、或稿子和图片现在的 hash 和它对不上 → fail「稿子在检查之后改过：先运行 leafpress work back <编号> 4 重新跑检查」。
2. 同 gate 的 1、2 两步（检查仓库、拉最新）。
3. 复制稿子和图片；再跑一次 `pnpm content:check`（拉下来的新文章可能撞 slug）；没过 → 还原、fail。
4. `git add -- <目标路径>`；`git commit -m "post: <中文稿的 title>"`；`git push origin main`。
5. 推送失败 → `git reset --mixed HEAD~1` 撤掉自己的提交、删掉目标文件，仓库回到拉完最新时的样子 → fail「推送失败：<原因>」。
6. 成功 → 写 `{folder}/.publish.json`（`{ slug, commit, pushedAt }`）→ `{ kind: "done", note: "已推送（提交 <前 7 位>）" }`。

**等上线并归档链接（archive）**

1. `url = <站点>/posts/<slug>/`。
2. 每 15 秒 GET 一次（单次 10 秒超时，每轮 `heartbeat()`），最多 10 分钟：200 → `{ kind: "done", url, publishedAt: today, localPath: <仓库>/content/posts/zh/<slug>.mdx, sourceRef: "zh/<slug>", note: "已上线" }`。
3. 10 分钟还没 200 → fail「推送了，但 10 分钟内还没上线；过一会儿再运行 leafpress work run <编号>」。

共享规则的 `applyCodeResult` 要把 done 里的 `localPath`、`sourceRef` 写到作品上（`CodeOutcome` 已由主控加了这两个字段）。

## Umami（`umami/`）

**共享链接**：`parseShareUrl(url)`：`https://cloud.umami.is/analytics/us/share/<共享编号>?…` → `apiBase = https://cloud.umami.is/analytics/us/api`，`shareId = <共享编号>`（规则：`/share/` 前面的路径加 `/api`）。格式不对 → 错误「Umami 共享链接的格式不对」。共享编号和换来的令牌都是密钥：只在内存里，不进任何输出、记录、文件。

**客户端** `createUmamiClient({ fetch, shareUrl, timezone = "Asia/Shanghai", sleep?, now? })`：

- `auth()`：GET `{apiBase}/share/{shareId}`，请求头 `Accept: application/json`、`x-umami-share-context: 1` → 网站编号和令牌（字段名以作者 9 月 25 日的采集脚本 `C:\code\yeton-blog\.fleet\reports\2026-09-25-traffic\analytics\collect-umami.ps1` 为准）。
- 数据请求另带 `x-umami-share-token: <令牌>`：
  - `stats(startAt, endAt)`：`/websites/{id}/stats?startAt&endAt&unit=day&timezone`
  - `pageviews(startAt, endAt)`：`/websites/{id}/pageviews?…&unit=day&timezone`（一次最多 221 天，超过就分段）
  - `expandedPaths(startAt, endAt)`：`/websites/{id}/metrics/expanded?type=path&startAt&endAt&timezone&limit=100&offset=…`，一页不满 100 行就停；行字段 `name, pageviews, visitors, visits, bounces, totaltime`
- 时间：`startAt` = 那天本地 0 点的毫秒，`endAt` = 次日 0 点减 1 毫秒。
- 节流和重试：两次请求间隔至少 200 毫秒；单次 10 秒超时；超时、网络错误、5xx、429 → 退避重试（0.5、1、2 秒，最多 3 次）；401、403 → 认证错误（共享链接被关掉或换了）。

**拿数据工具** `createUmamiDataTool(): DataTool`：

- 没配共享链接 → `{ ok: false, reason: "Umami 共享链接还没配", fixHint: "在账号详情 · 接入里填" }`；认证错误 → `{ ok: false, reason: "Umami 共享链接打不开了（可能被关掉或换了）", fixHint: "在 Umami 后台重新生成共享链接，填到接入里", expiredKey: "umami-share" }`；其余失败 → 原因写清（不带令牌）。
- `yesterday = today - 1`。起点：`lastSnapshotDay` 有值 → 从它开始（重拉这一天，覆盖写没问题）；没有 → 第一次接上，补历史：先用 `pageviews` 拉 `today - DATASET_DAYS` 到昨天的全站日序列，从第一天有数据的日期开始。起点晚于昨天 → `{ ok: true, result: { account: [], works: [], note: "已是最新" } }`。
- **账号每天**：`pageviews` 日序列（起点到昨天）→ 每天 `{ day, followers: null, reads: <当天全站访问> }`（博客没有订阅数；interactions 不给，按作品之和算，博客为 0）。
- **作品累计**：只认这个账号作品里、链接是本站中文地址 `/posts/<slug>/` 的作品（英文地址和改过 slug 的旧地址不计，用户定只看中文版）。
  - 昨天的累计：`expandedPaths(2000-01-01, 昨天)` → 每篇 `{ pageviews, visitors }`，快照日 = 昨天。
  - 起点到前天的每一天（补历史、或漏拉了几天时）：每天一次单日 `expandedPaths` 拿当天每篇的访问，从昨天的累计往回减出每天的累计访问；这些天的快照只有 `pageviews`（访客不能逐日相加，不写）；累计为 0 的天不写。
- 进度：补历史时每 10 天调一次 `ctx.progress?.("补历史：第 i/n 天")`。
- `note`：「入库 <n> 篇文章」，补了历史时「入库 <n> 篇文章，补了 <m> 天历史」。
- 请求数：平常每天约 6 次；第一次补历史约 190 次（博客从 2026-04-01 才有数据），一两分钟。

## 关键决策

1. **检查和推送分两步，检查后还原仓库**：检查要跑好几分钟（含构建），中途断了也不会把半截文件留在作者的博客仓库里；推送前核对稿子没被改过，保证推上去的就是检查过的。
2. **推送失败撤回自己的提交**：仓库回到推送前的样子，作者不用手动收拾。
3. **等上线再归档**：Cloudflare 构建要几分钟，链接能打开才算发出去了。
4. **用共享链接拿数据**：作者 9 月 25 日就这么拿过，只读、不用另外申请密钥；链接按密钥存。
5. **历史从累计往回减**：每篇文章的累计访问只查一次全量，往前每天只查当天，请求数最少，且累计数准确；访客数不能逐日相加，历史上只记访问。
6. **只看中文地址**：用户定。英文版照常写、照常发，数据不计。
