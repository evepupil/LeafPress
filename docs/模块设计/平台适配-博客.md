## 博客仓库的事实（侦察和评审实测）

- 文章：`content/posts/{zh,en}/<slug>.mdx`（`.md` 也算文章），slug 就是去掉扩展名的文件名；frontmatter 必填 `title`、`description`（240 字以内）、`published`（带引号的 `"YYYY-MM-DD"`，不带引号会被读成日期对象而校验不过）、`locale`（中文 `"zh-CN"`、英文 `"en"`）、`tags`（至少一个、不重复）；可选 `draft`、`pinned`、`updated`、`image`、`translationKey`；中英文靠 `translationKey` 配对，译文配对键也不能和别的文章撞。
- 网址：中文 `<站点>/posts/<slug>/`，英文 `<站点>/en/posts/<slug>/`；站点 `https://blog.chaosyn.com`。
- 上线：推到 `main` 后 Cloudflare Pages 自动构建（几分钟）。Notion 同步由 GitHub Action 在线上提交，本地会落后。
- 本机的 pnpm 是 npm 装的 `.cmd` 外壳：Node 24 不经过 shell 直接起 `pnpm.cmd` 会报 `spawn EINVAL`，要用 `cmd.exe /d /s /c pnpm <固定参数>` 起。

## 博客检出、仓库锁、外部命令（`checkout.ts`、`lock.ts`、`pnpm.ts`）

**检出目录**：`<数据目录>/blog-checkout/<账号编号>/`，是作者仓库的一个 git worktree（共用历史，不碰作者工作区）。

```ts
/** 把检出目录准备到线上最新的 main：fetch → 没有就 worktree add，有就 checkout --detach origin/main + clean（保留 node_modules）→ 依赖 */
export function prepareCheckout(input: { repo: string; dir: string; exec: ExecFn; heartbeat?: () => void }): Promise<{ base: string /* origin/main 的提交号 */ }>;
```

1. `git -C <仓库> fetch origin`（环境 `GIT_TERMINAL_PROMPT=0`、`GIT_SSH_COMMAND=ssh -o BatchMode=yes`，超时 2 分钟）。
2. `git -C <仓库> worktree prune`；检出目录不存在 → `git -C <仓库> worktree add --detach <目录> origin/main`；存在 → 在里面 `git checkout --detach --force origin/main`、`git clean -fdx -e node_modules`；任何一步出错就 `git worktree remove --force` 后重建一次。
3. 依赖：检出目录的 `pnpm-lock.yaml` 内容和上次装依赖时（记在 `<目录>/.leafpress-lock-hash`）不同、或没有 `node_modules` → `pnpm install --frozen-lockfile --offline`（10 分钟）；离线装不上再试 `--prefer-offline`；还不行 → 错误「博客的依赖装不上：先在博客仓库里运行 pnpm install」。
4. 返回 origin/main 的提交号。

**博客仓库锁**：`<数据目录>/locks/blog-<账号编号>/`（目录锁，里面写 `{ pid, startedAt, step, workId }`）。拿不到时：持有者进程还活着且开始不到 60 分钟 → 立即返回失败「博客仓库正在被另一次「<步骤>」使用（作品 <编号>，<时分> 开始），等它跑完再试」；否则当作上次异常退出留下的，按 M1 目录锁的墓碑改名办法接管。三个步骤和导入都要先拿这把锁，`finally` 里释放。

**pnpm**：`runPnpm(exec, cwd, args, timeoutMs)`：Windows 上 `cmd.exe /d /s /c pnpm <args>`（args 只用代码里写死的脚本名和 LeafPress 生成的路径，不拼用户输入），别的系统直接 `pnpm`。超时要连同子进程一起结束：`src/shared/exec.ts` 加一个选项 `killTree`，超时时 Windows 用 `taskkill /T /F /PID <pid>`，别的系统杀进程组。

## 三个代码步骤（`steps/`，按 `blog-write/<步骤>` 登记）

公共：仓库 = 配置 `repo-path`，站点 = `site-url`（去掉末尾的 `/`；缺了直接 fail「博客仓库位置还没配」「站点地址还没配」）。稿子文件：`中文稿.mdx`、`英文稿.mdx`、`slug.txt`、`images/` 下全部文件（可以没有）。目标路径（都在检出目录里）：`content/posts/zh/<slug>.mdx`、`content/posts/en/<slug>.mdx`、`public/images/posts/<slug>/`。外部命令的输出写进结果前用 `redactSecrets` 抹密钥。

**跑博客检查（gate）**

1. 先校验稿子（不碰仓库）：slug 匹配 `^[a-z0-9]+(?:-[a-z0-9]+)*$`；两篇稿子存在且不空；`images/` 里没有符号链接、没有跑出文件夹的路径；用 gray-matter 读两篇的 frontmatter：`draft` 为 true → fail「稿子写了 draft: true，博客不会显示，改成 false」；`locale` 分别是 `zh-CN`、`en`；`published` 是 `YYYY-MM-DD` 字符串；两篇 `translationKey` 相同。
2. 拿博客仓库锁；`prepareCheckout`。
3. 撞车检查（在检出目录里）：`content/posts/{zh,en}/` 下去掉扩展名同名的 `.md` / `.mdx`、全部文章里相同的 `translationKey`、`public/images/posts/<slug>/` 已存在 → fail「slug 撞了已有文章：<路径>，改 slug.txt 里的 slug 再跑」。
4. 复制稿子和图片（只新建，不覆盖）；`runPnpm exec prettier --write <目标文件>`。
5. 依次跑 `content:check`（2 分钟）、`format:check`（3 分钟）、`build`（8 分钟）；每项开跑前 `heartbeat()`；第一项没过就停。（作者的写博客 skill 还跑 lint、typecheck、test：这几项只查代码，推送后博客的 CI 会跑，这里不跑，控制在 10 分钟内。）
6. 把排好版的两篇复制回任务文件夹；写 `检查结果.txt`（每项：通过 / 没过、用时；没过的那项附最后 80 行输出）。全过才写 `.gate.json`：`{ passed: true, slug, hash, base, checkedAt }`，hash = 对「`slug.txt`、两篇稿子、`images/` 下全部文件」按相对路径排序后，逐个把「相对路径 + 内容」喂给 sha256。
7. 释放锁。检出目录不用还原（下次准备时会重置）。
8. 全过 → done（note「博客检查全过」）；没过 → fail「博客检查没过：<哪一项>（详情在 检查结果.txt）」。

**提交并推送（publish）**——可以安全地重复执行

1. `.gate.json` 不存在、`passed` 不是 true、或 hash（含 slug）和现在的稿子对不上 → fail「稿子在检查之后改过：先运行 leafpress work back <编号> 4 重新跑检查」。
2. 拿锁；`prepareCheckout`。
3. 线上已经有这篇：检出目录里 `content/posts/zh/<slug>.mdx` 存在 → 内容和任务文件夹里排好版的中文稿完全相同 → 当作已推送：写 `.publish.json`（提交号取 `git log -1 --format=%H -- <路径>`），done（note「线上已经有这篇了，按已推送处理」）；内容不同 → fail「slug 撞了已有文章」。
4. 复制稿子和图片；`content:check`；没过 → fail（检出目录下次会重置，不用收拾）。
5. 提交：`git add -- <目标路径>`；`git commit -m "post: <中文稿 title>" -- <目标路径>`（只提交这几个路径）。用户名、邮箱用作者仓库的 git 配置；提交失败（没配用户名、钩子……）→ fail 并写明原因。
6. 推送：`git push origin HEAD:main`（同 fetch 的环境变量，超时 2 分钟）。
   - 被拒（线上前进了）→ `git fetch origin`、`git rebase origin/main`、再跑一次 `content:check`、再推一次（最多重试 2 次）。
   - 超时或结果不明 → `git fetch origin`，用 `git merge-base --is-ancestor <本次提交> origin/main` 判断：已经在线上 → 当作成功；不在 → fail「推送没成功，线上没有这次提交，可以重新运行 work run」。
7. 写 `.publish.json`（`{ slug, commit, pushedAt }`）；释放锁；done（note「已推送（提交 <前 7 位>）」）。

**等上线并归档链接（archive）**

1. `url = <站点>/posts/<slug>/`。
2. 每 15 秒 GET 一次（单次 10 秒超时，每轮 `heartbeat()`），最多 3 分钟：200 → done：`url`、`publishedAt` = 中文稿 frontmatter 的 `published`、`localPath = <作者仓库>/content/posts/zh/<slug>.mdx`、`sourceRef = "zh/<slug>"`、note「已上线」。
3. 3 分钟还没 200 → fail「推送了，还没上线（Cloudflare 一般要几分钟）；过两三分钟再运行 leafpress work run <编号>；超过半小时还不行，去 Cloudflare Pages 看部署记录」。
4. 网络请求和等待用代码步骤上下文里注入的 `fetch`、`sleep`（`CodeStepContext` 加这两项；`createPlatformRuntime(options?: { fetch?, sleep? })` 接参数，缺省用全局 fetch 和真的等待），测试里不真等。

共享规则的 `applyCodeResult` 要把 done 里的 `localPath`、`sourceRef` 写到作品上。

## Umami（`umami/`）

**共享链接**：`parseShareUrl(url)`：`https://cloud.umami.is/analytics/us/share/<共享编号>?…` → `apiBase = https://cloud.umami.is/analytics/us/api`、`shareId`（`/share/` 前面的路径加 `/api`）。格式不对 → 错误「Umami 共享链接的格式不对」。

**客户端** `createUmamiClient({ fetch, shareUrl, timezone = "Asia/Shanghai", sleep? })`：

- `auth()`：GET `{apiBase}/share/{shareId}`，请求头 `Accept: application/json`、`x-umami-share-context: 1` → 网站编号和令牌（字段名以作者的采集脚本 `C:\code\yeton-blog\.fleet\reports\2026-09-25-traffic\analytics\collect-umami.ps1` 为准）。
- 数据请求另带 `x-umami-share-token`：`stats`、`pageviews`（`unit=day`，一次最多 221 天，超过就分段）、`expandedPaths`（`metrics/expanded?type=path`）。
- **全量路径一次取够**：`expandedPaths` 用很大的 `limit`（先试 5000）一次取完；返回行数等于 limit 时才分页，分页结果按路径名去重，并用普通 `metrics?type=path`（一次取 1000 以上）的完整路径名集合核对，缺名或重名就整次重试一次，仍不对就整次失败。（评审在作者 9 月 25 日的原始数据里发现：按 100 行分页时，访客数相同的页面会在两页之间重复和漏掉。）
- 时间：`startAt` = 那天本地 0 点的毫秒，`endAt` = 次日 0 点减 1 毫秒。
- 节流和重试：间隔至少 200 毫秒；单次 10 秒超时；超时、网络错误、5xx、429、返回的不是 JSON → 退避重试（0.5、1、2 秒）；数据接口 401、403 → **先重新取一次令牌再重试同一请求**；只有取令牌这一步被拒（401、403、404）才算共享链接失效。
- 错误文字一律不带请求地址，并由客户端自己抹掉共享编号、令牌、网站编号。

**拿数据工具** `createUmamiDataTool(): DataTool`：

- 没配共享链接 → `{ ok: false, reason: "Umami 共享链接还没配", fixHint: "在账号详情 · 接入里填" }`；共享链接失效 → `{ ok: false, reason: "Umami 共享链接打不开了（可能被关掉或换了）", fixHint: "在 Umami 后台重新生成共享链接，填到接入里", expiredKey: "umami-share" }`；其余失败写清原因。**任何一步失败都整次失败，不写半截数据。**
- **路径对作品**：只认本站中文文章地址。比较前两边都规范化：URL 解码、去掉查询串和 `#` 锚点、统一以 `/` 结尾；原始行先按路径名去重，再按规范化后的路径合并求和。英文地址、别的页面不计。
- `yesterday = today - 1`。**起点**：
  - 这个账号对得上的作品里有还没有任何累计数据的（作品的 `totalsDay` 为空，比如刚导入的、刚发的）→ 补历史：起点 = 下面三个里最晚的：「`today - DATASET_DAYS`」（半年窗口第一天）、「全站第一天有数据的日期」（用 `pageviews` 日序列找）、「这些作品里最早的发布日期的前一天」（没有发布日期或写得不对的按窗口第一天）。所以第一次导入后补满半年，以后每发一篇新文章只补它发布前一天到昨天的几天（实测：新文章发布后的下一次拉取 4 次请求、补 2 天）。两条保护：账号从没拉过时不按发布日期收窄（账号每天的数是全站的访问，和文章什么时候发无关，要补满半年）；账号拉过时，起点不晚于「上次拉到的后一天」，中间不漏天（规则在 `umami/history-start.ts`）；
  - 否则起点 = `lastSnapshotDay + 1`（不重拉上次的最后一天；早于窗口第一天时从窗口第一天算）；没有 `lastSnapshotDay` 时同补历史。
  - 起点晚于昨天 → `{ ok: true, result: { account: [], works: [], note: "已是最新" } }`。
- **账号每天**：`pageviews` 日序列（起点到昨天）→ 每天 `{ day, followers: null, reads: <当天全站访问> }`。
- **作品累计**（算法写死，附例子）：
  - 昨天：`expandedPaths(2000-01-01, 昨天)` → 每篇 `{ pageviews, visitors }`，快照日 = 昨天。
  - 起点到前天的每一天 d：`累计(d) = 累计(昨天) − Σ 当天访问(d+1 … 昨天)`，所以单日请求的日期是「起点后一天到昨天」。例：10/8 累计 100，10/8 当天 5、10/7 当天 3 → 10/7 结束时累计 95、10/6 结束时累计 92。这些天的快照只有 `pageviews`（访客不能逐日相加）。
  - 校验：每篇的累计不能是负数、按日期不能下降，不满足 → 整次失败「Umami 的数前后对不上，这次没入库」。
  - 累计为 0 的天不写；每篇在第一次出现非零累计的前一天写一条全 0 快照（让第一天的访问算进当天的新增；共享规则把每篇的第一条快照当起点），**但只在能确认那天累计确实是 0 时才写**：那天在这次查的范围里；或者这篇第一次入库、且全站累计等于起点以来的日序列合计（起点之前全站没有访问）。照字面每次都写会出两个错：平常拉时把上次最后一天的真实快照盖成 0；第一次补历史（窗口从 4 月 10 日起、博客 4 月 1 日起就有数据）会把老文章窗口之前攒下的访问全算成窗口第一天的新增。
  - 这次查到的路径里没有的作品（还没人看过）：给昨天写一条访问 0、访客 0 的快照，这样它有了累计数据，下次不会再触发补历史；它已有的累计比 0 大时（地址可能改过）不写，按下一条处理。
  - 昨天的累计比记录库里这篇现有的 `totals.pageviews` 小（Umami 免费版只保留 6 个月，旧数据会被清）→ 这篇这次不写，note 里写出编号。
  - 没配站点地址时照样按路径对作品（不比主机名）；站点地址写成了不是网址的东西才失败。
- 进度：补历史时每 10 天调一次 `ctx.progress?.("补历史：第 i/n 天")`；用例抹掉密钥后交给 `pullData` 的 `onProgress`，命令行打到标准错误，一行「<账号>：<原话>」。
- 整个窗口里全站一点访问都没有时（刚接上的新站）直接回「已是最新」，没访问的作品这时不记 0（每次只 2 次请求，不拖慢）。
- `note`：「入库 <n> 篇文章」；补了历史时「入库 <n> 篇文章，补了 <m> 天历史」。
- 请求数：平常每天约 3～4 次、十秒左右；第一次补历史实测 188 次、约 4 分 40 秒（服务器单次响应常 1～2 秒，偶尔 10 秒以上甚至 90 秒，靠重试撑过去）。`expandedPaths` 的 limit 实测没有上限，客户端取 5000。

## 关键决策

1. **检查和推送在单独的检出目录里做**（评审后改）：作者的工作区不动，作者同时在仓库里写东西、本地有没推送的提交、暂存了文件，都不受影响；中途断电、超时、被杀，只会在 LeafPress 自己的目录里留下垃圾，下次准备时自动重置。
2. **推送可以安全地重复执行**：先看线上有没有这篇，结果不明时到线上核对；不会推两次，也不会把推成功的当失败撤回。
3. **一把博客仓库锁**：两个作品同时跑检查、或 agent 超时后重跑时，后来的直接告诉你「正在跑」，不会互相踩。
4. **检查只跑内容、格式、构建三项**：只动文章文件，代码检查推送后由博客的 CI 跑；控制在 10 分钟内，agent 的命令不会被工具超时打断。
5. **等上线最多 3 分钟**：没上线就让 agent 过一会儿再跑，不长时间占着命令。
6. **用共享链接拿数据、历史从累计往回减**：作者 9 月 25 日就这么拿过；只查一次全量累计，往前每天只查当天，请求最少、累计准确；访客数不能逐日相加，历史上只记访问。
7. **只看中文地址**：用户定。英文版照常写、照常发，数据不计。

真实环境里实测过的：

- **检出冒烟**（作者的博客仓库，只 fetch 和建工作树）：第一次准备检出目录 63 秒，之后 5 秒；`content:check` 10.7 秒、`format:check` 16.5 秒、`build` 241 秒；作者工作区前后没有任何改动。
- **Umami 只读冒烟**：只拉昨天 3 次请求、8 秒左右，292 个页面里对上 37 篇中文文章（仓库里已发布 40 篇，另 3 篇中文地址上没有访问）；往回减的公式拿真实数据核对 292 个页面 × 3 天，0 处不一致；完整补一次半年历史 182 天、188 次请求、约 4 分 40 秒、37 篇共 2217 条快照、没有失败。

## 验证方式

单测在 `tests/platforms/blog/`：

1. 定义：`pickWorkflow("blog", …)` 配博客写稿；`missingHandlers` 为空。
2. 检出和锁：用临时仓库 + 本地裸仓库当远程：第一次 `prepareCheckout` 建 worktree、第二次重置（检出目录里的垃圾文件被清掉、node_modules 保留）、锁文件变了才重装（假的 exec 记录调用）；**作者工作区的文件、暂存区、本地领先的提交在整个过程中一个字节不变**（每个步骤测试前后都对比）。锁：被活着的进程占着时立即失败、持有者已退出时接管。
3. 三个步骤（git 走真的，pnpm 换成假的；假 pnpm 可以控制成功 / 失败 / 超时）：
   - gate：稿子校验的每种失败；撞车（同名 `.md`、同 translationKey、图片目录）；全过时的 `检查结果.txt`、`.gate.json`（含 passed、slug、hash）、排好版的稿子复制回来；某项没过不写 `.gate.json`；
   - publish：hash 或 slug 对不上 fail；正常推送后远程有这次提交且只含目标路径；远程前进了一次（推送被拒）后变基重推成功；推送超时但其实已到远程 → 当作成功；线上已有同内容文章 → 当作已推送；作者工作区不变；
   - archive：假 fetch 先 404 两次再 200 → done 带 url、localPath、sourceRef、publishedAt 取 frontmatter；一直 404 → fail（注入 sleep，不真等）。
4. Umami 客户端：认证；三个接口的参数；大 limit 一次取完；分页时去重和核对；超时和 5xx 重试；429 退避；数据接口 401 先重取令牌再成功；取令牌被拒 → 失效；错误文字里没有共享编号、令牌、网站编号和地址。
5. 拿数据工具：补历史（假数据 5 天，逐天核对累计 = 昨天累计减后面每天的单日访问；第一次非零前一天有全 0 快照；昨天带访客）；平常一天；漏了 3 天；有新导入作品时退回补历史；已是最新；路径规范化（无结尾斜杠、带锚点、中文 slug 编码和解码两种写法、原始重复行）；累计下降 → 整次失败；Umami 数据被清导致累计变小 → 这篇不写；没配、失效。
6. 端到端：在临时数据目录里，用临时博客仓库加本地裸仓库当远程、假的 Umami 接口，跑通「导入 → 拉数据（含补历史）→ 新作品过检查、推送、归档 → 再拉一次」。

开发只用临时数据和假接口验证，不碰作者真实的博客仓库、Umami 和 LeafPress 数据目录。真实环境上导入文章、补数据、发文章，是作者用的时候让 AI 做的事。2026-10-09 开发时对真实环境做过一次只读核对，结果记在「当前实现」，以后不再作为验证步骤。
