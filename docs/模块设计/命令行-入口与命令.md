# 命令行 · 入口与命令

> 模块定位：`leafpress` 命令的入口、输出约定、M0 的几个子命令和浏览器定位 · 对应代码：`src/cli/`、`src/assets/browser.ts` · 所属里程碑：[M0 地基](../roadmap.md#m0-地基) · 状态：已完成 · 最近更新：2026-10-05

## 职责与边界

- 管：参数解析；把下层的结果变成给人看的中文或给 skill 读的 JSON；退出码；`init`、`doctor`、`posts`、`run list / show / cancel` 四组命令；找本机 Edge。
- 不管：业务规则。命令里只组装和输出，判断都在下层（配置、记录库、平台接入、工作流）。

## 结构与数据流

| 文件 | 说明 |
|---|---|
| `src/cli/main.ts` | 入口，第一行 `#!/usr/bin/env node`；导出 `buildProgram()` 供测试；`main(argv)` 负责统一的错误处理和退出码。判断「是否被直接运行」用 `import.meta.main`：经全局安装的符号链接或目录联接启动时，命令行里的路径和文件真实路径不同，逐字比较会让命令静默不执行 |
| `src/cli/context.ts` | `createCliContext(globalOptions, deps?)`：按需创建并缓存数据目录、配置、记录库、平台登记表、工作流引擎；`close()` 关闭记录库 |
| `src/cli/output.ts` | 显示宽度计算（汉字等全角字符算 2 列）、按宽度截断、对齐表格、输出 JSON |
| `src/cli/commands/init.ts`、`doctor.ts`、`posts.ts`、`run.ts` | 每个命令一个文件：`register(program, getContext)` 负责登记命令；`execute*` 返回结果对象；`render*` 把结果对象变成给人看的文字 |
| `src/assets/browser.ts` | `locateEdge(options)` 找本机 Edge |

「执行」和「显示」分开写：`execute*` 只返回数据，便于单测；`--json` 时直接输出这个数据对象，否则用 `render*` 的文字。

### 全局约定

- 全局选项：`--home <目录>`（数据目录，优先级最高）、`--json`。`leafpress --version` 输出 `package.json` 里的版本号（运行时用 `createRequire` 读，不要用 import 把它编进构建）。
- 依赖都从下层拿：数据目录用 `resolveHome`；配置用 `loadConfig`；记录库用 `openStore(homePaths(home).dbFile)`；平台登记表用 `createDefaultRegistry({ blog: config.blog })`；工作流引擎用 `createWorkflowEngine({ store: store.runs, workflows: WORKFLOWS, runsDir })`。
- 退出码：成功 0；运行出错 1（包括体检有 error 级问题）；用法错误 2（参数不对、`USAGE` 错误）。用法错误的 message 要附上具体原因（比如「未知选项 --limt」「缺少运行编号」），不能只说「参数不正确」。
- 出错时（给人看）往标准错误写两行：`错误：<message>`、`提示：<hint>`（没有 hint 就只写一行）。`--json` 时往标准输出写 `{ "ok": false, "error": { "code", "message", "hint" } }`。
- 不是 `LeafPressError` 的异常：message 写「内部错误：」加原始 message，hint「设置环境变量 LEAFPRESS_DEBUG=1 可以看到详细信息」；只有设了这个环境变量才打印调用栈。
- 成功时 `--json` 输出 `{ "ok": true, ...结果对象 }`。
- 命令结束前一定关闭记录库。

### `leafpress init --blog <博客仓库路径> [--site-url <网址>]`

1. 数据目录不存在就建。
2. 配置已存在：不改动，输出「配置已存在，没有改动」和路径。
3. 配置不存在：`--blog` 必填（缺了按用法错误处理）；路径必须存在、根目录下有 `.git`、并且有 `content/posts` 目录，否则抛 `USAGE`，hint 说明缺了什么。`--site-url` 给了就先校验是合法的 http(s) 网址，不合法抛 `USAGE`。`--home` 指向一个已存在的文件时抛 `USAGE`（「数据目录的位置被一个文件占了」）。写入的配置：`{ version: 1, blog: { repoPath: <绝对路径>, siteUrl?: <网址> } }`，其余用默认值。
4. 打开一次记录库（完成建表）。
5. 输出数据目录、配置文件、记录库文件三个路径，以及下一步建议「运行 leafpress doctor 检查环境」。

### `leafpress doctor`

逐项检查，每项给出级别 `ok`、`warn` 或 `error`，加一句说明，必要时加修复建议。**任何一项的说明和建议里都不得出现密钥的值。**

| 编号 | 检查项 | 规则 |
|---|---|---|
| `node` | Node 版本 | 低于 24.2 为 error |
| `config` | 配置 | 不存在为 error，建议运行 `leafpress init`；存在但校验不过（拼错字段、JSON 写坏）为 error，说明和建议照搬下层的 message 和 hint（列出要改的字段），不要建议 init（init 不会覆盖已有配置）。两种情况下后面依赖配置的检查都跳过 |
| `store` | 记录库 | 用 `inspectStore` 只读查看，**不打开写、不建库、不升级**：文件不存在为 warn（建议运行 `leafpress init`）；版本低于代码认识的版本为 warn（说明下次运行其他命令时会自动备份并升级）；版本高于代码为 error（建议升级 LeafPress）；读不了为 error；正常时说明表结构版本 |
| `blog-repo` | 博客仓库 | 不是 git 仓库为 error；有改动为 warn；正常时说明分支、比远程多几个少几个（按本地已有的远程跟踪分支，不联网），并建议用 `leafpress posts --sync` 拉最新 |
| `blog-posts` | 博客原稿 | 列不出来为 error；正常时说明各语言目录的篇数；有元数据问题为 warn，说明有几篇 |
| `blog-site-url` | 博客网址 | 没配为 warn（知乎版文末的原文链接要用它） |
| `zhihu-openapi` | 知乎发布凭证 | 用 `checkZhihuOpenApi`；ok 为 ok，其余为 warn，说明照搬它的 detail |
| `zhihu-publisher-skill` | 知乎官方发布 skill | `<用户目录>/.claude/skills/zhihu-publisher/SKILL.md` 存在为 ok，否则 warn |
| `zhihu-uploader-skill` | 知乎图片上传 skill | `<用户目录>/.claude/skills/zhihu-mediacloud-uploader/SKILL.md` 存在为 ok，否则 warn，建议 `npx skills add zhihu/zhihu-mediacloud-uploader.git -g` |
| `zhihu-developer` | 知乎数据接口密钥 | 用 `checkZhihuDeveloper`；ok 为 ok，其余为 warn |
| `browser` | 浏览器 | `locateEdge` 找到为 ok 并显示路径，找不到为 warn |

- 每一项检查各自捕获异常：某一项出错（比如凭证文件没权限读）只把这一项记为 warn 或 error 并说明原因，其他项照常检查，体检本身不中断。
- 读博客仓库状态的 git 命令要带 `--no-optional-locks`，否则 `git status` 会顺手改写仓库的索引文件。
- 给人看的输出：一张三列表格「检查项 | 状态 | 说明」，状态用 `✓`、`!`、`✗`；表格下面逐条列出各项的修复建议；最后一行总结「有 N 项需要处理」或「全部正常」。
- JSON：`{ ok, checks: [{ id, label, level, detail, hint? }] }`，`ok` 为「没有 error 级问题」。
- 有 error 级问题时退出码为 1。

### `leafpress posts [--sync] [--locale <语言目录>|all] [--limit <篇数>]`

1. 带 `--sync` 时先调博客的 `sync()`，把结果的 message 放在输出最前面；拉取失败不中断，接着用本地内容。
2. `list()` 列出原稿；按 `--locale` 过滤，缺省是配置的 `blog.primaryLocaleDir`，`all` 表示不过滤；`--limit` 取最新的前几篇。
3. 在一个事务里把这些原稿逐个 `sources.upsert` 进记录库（平台 `blog`，类型 `article`）。
4. 发布目标 = `registry.publishTargets({ excludePlatforms: ["blog"] })`，现在是知乎长文、知乎回答两个。
5. 用 `publicationOverview` 查出这些原稿的版本和发布记录，对每篇原稿、每个目标算出状态（已放弃的版本不算）：

| 状态 | 条件 | 表格里显示 |
|---|---|---|
| `published` | 有已发布的记录 | 「已发」，多于一条时「已发 N」 |
| `pending` | 没有已发布，但有发布意图记录（上次发布结果未知） | 「发布中」 |
| `unverified` | 没有已发布和发布意图，但有待核实的记录 | 「待核实」 |
| `in-progress` | 都没有，但有草稿或待确认的版本 | 「进行中」 |
| `none` | 什么都没有 | 「—」 |

6. 给人看的输出：表格列为「日期 | 标题 | 来源 | <平台名>·<形态名> ...」，目标列按发布目标的顺序自动生成（以后加平台会自动多一列）；来源显示「Notion」或「仓库」；标题先把换行等空白折成一个空格，按显示宽度截断，草稿再在截断后的标题后面加「（草稿）」，标题加标记合计不超过 40 列，超出用「…」。显示宽度：汉字、全角字符、按两列显示的 emoji 算 2 列，组合附加符号和零宽字符算 0 列。表格后一行汇总「共 N 篇；知乎·长文 已发 x 篇，知乎·回答 已发 y 篇」。有元数据问题时再列出「有 k 篇元数据有问题」和每条的路径与说明。
7. JSON：

```json
{
  "ok": true,
  "sync": { "action": "...", "message": "..." },
  "sources": [
    {
      "ref": "zh/xxx",
      "title": "...",
      "publishedAt": "2026-09-30",
      "origin": "notion",
      "draft": false,
      "targets": [
        { "platform": "zhihu", "format": "article", "label": "知乎·长文", "state": "none", "count": 0, "urls": [] }
      ]
    }
  ],
  "issues": [{ "path": "...", "message": "..." }]
}
```

`sync` 只在带 `--sync` 时出现。

### `leafpress run list [--all]`、`run show <运行编号>`、`run cancel <运行编号>`

- `list`：缺省只列没结束的（运行中、等待中、失败），`--all` 列全部。表格「编号 | 工作流 | 状态 | 停在 | 更新时间」，状态显示中文（运行中、等待中、已完成、失败、已取消），更新时间显示本地时间到分钟。
- `show`：运行的基本信息，加每一步的「序号 | 步骤 | 种类 | 状态 | 次数」；等待中时列出在等什么和相关文件路径；失败时列出错误。
- `cancel [--force]`：调引擎的 `cancel`，输出取消后的状态。`--force` 只用于「运行中但租约已过期」（上次异常退出）的运行。
- 三个命令的 JSON 和其他命令一样带 `ok: true` 外壳：`list` 为 `{ ok, runs }`，`show` 为 `{ ok, run }`（引擎的运行详情），`cancel` 为 `{ ok, run }`（引擎的运行报告）。
- 三个命令都只读：数据目录或记录库还不存在时，`list` 输出「没有运行记录」（JSON 为空数组），`show`、`cancel` 报运行不存在，**不顺手建目录和库**。没有未结束的运行时，`list` 输出一句「没有未结束的运行」，不输出空表头。
- `run start`、`run resume` 等第一个正式工作流在 M1 加入。

### 找 Edge `src/assets/browser.ts`

`locateEdge({ configuredPath?, env, platform, exists })` 按顺序找第一个存在的：配置里的 `browser.executablePath`；Windows 上依次是 `%ProgramFiles(x86)%`、`%ProgramFiles%`、`%LOCALAPPDATA%` 下的 `Microsoft\Edge\Application\msedge.exe`；macOS 上 `/Applications/Microsoft Edge.app/Contents/MacOS/Microsoft Edge`；Linux 上 `/usr/bin/microsoft-edge`、`/usr/bin/microsoft-edge-stable`。都没有返回 undefined。`exists` 可注入，便于测试。

## 关键决策

1. 执行和显示分开：测试只断言数据，输出格式改了不用改一堆测试。
2. 发布状态总览的列从平台登记表自动生成：加平台不用改这个命令。
3. 体检不联网、不改任何东西：随时可以放心跑。唯一的例外是记录库旁边留着未并回的日志文件时（进程被强杀或别的进程正开着库），为了读准版本号会让 SQLite 改动 `-shm` 辅助文件（不存数据），见记录库模块文档。
4. 入口判断用 `import.meta.main`（Node 24.2 起才有），同时保留「比较真实路径」的兜底，所以最低支持的 Node 版本定为 24.2。

## 当前实现

| 文件 | 内容 |
|---|---|
| `main.ts` | 入口与统一的错误处理、退出码；用 `import.meta.main` 判断是否被直接运行，经全局安装的链接启动也能正常工作 |
| `context.ts` | 按需创建数据目录、配置、记录库、平台登记表、工作流引擎；只读命令不建库 |
| `output.ts` | 显示宽度（汉字、全角、两列 emoji 算 2，组合符、零宽字符算 0）、截断、表格、JSON |
| `commands/init.ts` | 初始化：校验博客仓库、网址、数据目录位置 |
| `commands/doctor.ts`、`doctor-inspections.ts` | 体检：11 项各自捕获异常，只读查看记录库，不改博客仓库 |
| `commands/posts.ts`、`posts-state.ts` | 发布状态总览：原稿在一个事务里入库，五种状态计算，标题清洗与截断 |
| `commands/run.ts` | 运行的列出、查看、取消 |
| `src/assets/browser.ts` | 找本机 Edge |

单测 57 个；另有集成测试（`tests/integration/`）用真实子进程跑完整命令流程。

经两轮独立评审（Sonnet）：17 种密钥场景 × 12 条命令 × 调试开关开关，共 408 次调用，没有出现任何密钥值；故意改坏实现的实验里，39 个改坏抓住 38 个。

最终验收（数据目录放在临时目录，对作者真实博客）：经目录联接启动正常；体检各项状态正确；74 篇原稿零问题；`posts --sync` 在工作区干净时把博客快进了 5 个提交，追上远程；用法错误给出具体原因、退出码 2。

## 验证方式

单测放在 `tests/cli/`、`tests/assets/`：

1. 显示宽度：中英文混排、全角标点；截断后宽度不超限且以「…」结尾；表格对齐。
2. 发布状态计算：上面五种状态各有用例，含已放弃版本被忽略、一篇原稿回答多个问题时显示「已发 2」。
3. `posts`：用临时目录造博客仓库和数据目录，注入到命令的执行函数里，断言结果对象；`--locale all`、`--limit`；重复执行时原稿不会重复入库。
4. `doctor`：用临时数据目录和注入的环境变量，覆盖配置缺失（error、退出码 1）、凭证缺失（warn）、全部正常；断言输出里不含密钥。
5. `init`：首次写配置、已存在不覆盖、博客路径不合法报用法错误。
6. 错误输出：`LeafPressError` 和普通异常两种情况下给人看和 JSON 两种格式；退出码 1 和 2。
7. `locateEdge`：注入 `exists` 覆盖每个候选位置和找不到的情况。

`pnpm gate` 全部通过；`pnpm build` 后 `node dist/cli/main.js --version`、`doctor`、`posts` 能实际跑。
