# 录屏与剪辑工具
> 调研日期：2026-10-01

说明：Star 数、最近提交日期、开源协议均为本次用 `gh api repos/<owner>/<repo>` 实际读到的值（读取时间 2026-10-01），出处见各条目「出处」。凡仓库内没有 LICENSE 文件的，协议写「未核实（仓库无 LICENSE 文件）」。

## 结论

1. **推荐链路（能让 Claude Code 全流程参与）**：
   **录屏用 Cap CLI / `cap mcp serve`**（`cap record start --mode studio --json` 起停、导出、有本地 MCP 和 skill，官方就是为 AI agent 做的）→ **粗剪用 auto-editor**（一条命令砍掉没说话的段落，纯命令行确定性工具，最适合 agent 批量跑）→ **成片交给 FFmpeg 脚本**（横版转竖版、加片头片尾、烧字幕），横竖两版都从同一份粗剪产物导出。（另：`browser-use/video-use` 是本次调研里唯一「让 AI 助手按对话自己下刀剪片」的成熟实现，但转写写死 ElevenLabs、无官方 Windows 支持、中文字幕默认渲染成方块，本次只当参考实现，不进主链路。）
2. **如果不想被 Cap 的账号/上传流程绑住**，录屏换成 **OBS Studio + obs-websocket**：OBS 28 起 obs-websocket 内置、默认端口 4455，再配一个 CLI（`obs-cmd` 有 Windows 二进制，MIT）就能让脚本/AI 助手开始停止录制、切场景；缺点是「自动跟随鼠标放大」这类成片效果要自己后期做。
3. **想要「录完自动跟鼠标放大、加背景阴影」的开箱效果，用 OpenScreen（getopenscreen/openscreen）**：MIT、三平台、有 headless CLI（`openscreen record --duration 20 --project demo.openscreen --json`），是 Screen Studio 这个品类里唯一活跃维护且有 CLI 的开源实现。注意老仓库 `siddharthvaddem/openscreen`（3.9 万星）**已归档**，别再往那儿提 issue。
4. **剪映这条路建议先别压重注**：pyJianYingDraft 生成草稿在剪映 5.9 上稳，但 6.0+ 起草稿主文件改名为 `draft_info.json`、内容加密，仓库主分支的修复 PR（#198）到 2026-09-10 仍是 open；自动导出依赖旧版可见控件，**剪映 7 及以上已失效**。要用就锁在剪映 6.8 或更低，或者改用 CapCut 国际版（pyCapCut 线，不加密）。
5. **别碰 `muesli/obs-cli`**（2023-03-15 后无提交，只支持 obs-websocket 4.x）和 `hey-jian-wei/jianying-mcp`（2025-08-22 后无提交，且 README 里的 clone 命令还是占位符 `your-username`）。

## 工具逐个说明

### OBS Studio（直播/录屏老牌底座）
- 地址：https://github.com/obsproject/obs-studio
- 形态：桌面软件（C/C++、Qt）
- 能做什么：屏幕/窗口/摄像头多源录制、场景切换、本地录制、推流、虚拟摄像头；插件生态最大。
- Windows 支持：官方一等公民，装 exe 即可，无额外依赖。
- AI 助手能否调用：能，但不是直接调。OBS 自身只提供启动参数 `--startrecording`、`--minimize-to-tray`、`--scene "name"`（只对启动那一刻有效，不能停止录制）。真正的接口是内置的 obs-websocket（见下一条）。
- 开源协议：GPL-2.0
- 活跃度：Star 76,841；最近提交 2026-10-01；未归档。
- 已知坑：命令行参数只能「启动时开始录」，停不下来；要精确控制必须走 WebSocket。https://obsproject.com/kb/launch-parameters
- 对委托人的价值：**高**。Windows 上最稳的免费录屏底座，且 WebSocket 接口成熟，是「AI 助手控制录屏」最可控的方案。
- 出处：https://github.com/obsproject/obs-studio ；https://obsproject.com/kb/launch-parameters ；`gh api repos/obsproject/obs-studio`

### obs-websocket（OBS 的远程控制协议，28 起内置）
- 地址：https://github.com/obsproject/obs-websocket
- 形态：协议/插件（自 OBS Studio 28.0.0 起内置，无需单独安装）
- 能做什么：StartRecord / StopRecord / SetCurrentProgramScene / ToggleRecord 等全套远程控制；默认监听 4455 端口（可在 Tools → 设置里改），协议文档在仓库 PROTOCOL.md。
- Windows 支持：随 OBS 一起内置，无额外安装。
- AI 助手能否调用：能，这是最直接的一条路——任何语言写个 WebSocket 客户端，或直接用现成 CLI：
  - `grigio/obs-cmd`：Rust，MIT，Star 360，最近提交 2026-08-26，Release 里有 `obs-cmd-x64-windows.tar.gz`；命令形如 `obs-cmd recording start` / `obs-cmd scene switch <scene>`。https://github.com/grigio/obs-cmd
  - `onyx-and-iris/obsws-cli`：Python（`pip install obsws-cli`），MIT，但 Star 只有 4、最近提交 2026-07-20，量级小。https://github.com/onyx-and-iris/obsws-cli
- 开源协议：GPL-2.0
- 活跃度：Star 4,357；最近提交 2026-09-28；未归档。
- 已知坑：5.x 与老的 4.x 协议**不兼容**，只支持 4.x 的客户端（如 muesli/obs-cli）在 OBS 28+ 上要另装 `4.9.1-compat` 插件。https://github.com/obsproject/obs-websocket/releases/tag/5.0.0
- 对委托人的价值：**高**。有它才能让 AI 助手「开始录、切场景、停录」，是 OBS 方案的钥匙。
- 出处：https://github.com/obsproject/obs-websocket ；https://obsproject.com/kb/remote-control-guide ；`gh api repos/obsproject/obs-websocket`

### Cap（开源 Loom 替代，官方自带 CLI + MCP）
- 地址：https://github.com/CapSoftware/Cap ；官网 https://cap.so
- 形态：桌面软件（Tauri + Rust）+ 命令行 CLI + 本地 MCP 服务 + AI 助手 skill
- 能做什么：屏幕/窗口/摄像头录制，Instant（边录边传，给分享链接）与 Studio（本地录、带背景/缩放/字幕的编辑器再导出）两种模式；自带 AI 生成标题、摘要、章节、字幕、转写；可接自有 S3 / Cloudflare R2 / Backblaze B2 / MinIO，可整套自托管。
- Windows 支持：官方支持 Windows 10 及以上（macOS 同样原生，Linux 是 .deb）。安装就是下 exe，不麻烦。
- AI 助手能否调用：**能，而且是本次调研里最完整的**。官方页面明确写了 CLI + 本地 MCP：`cap record start --screen 1 --mode instant --duration 20 --json`、`cap export ./recording.cap --quality 4k`、`cap upload ./recording.mp4 --json`；`cap mcp serve` 通过 stdio 暴露 76 个工具（库/转写/评论/分享/文件夹/分析/存储等）；一条命令装 skill 和 MCP：`cap agents install --target claude --component all --yes --json`（会写 `~/.claude/skills/cap/SKILL.md` 和 `~/.claude.json`）。录制、上传、密码、凭证故意留在 CLI，不走 MCP，所以密钥不进对话。
- 开源协议：**注意，不是单一协议**。LICENSE 里写明：`cap-camera*` 与 `scap-*` 系列 crate 是 MIT，其余内容为 **AGPLv3**（GitHub 因此显示 NOASSERTION）。官网文档里写 "permissive license" 与实际 LICENSE 不符，商业闭源二次分发要谨慎。
- 活跃度：Star 22,990；最近提交 2026-10-01；未归档。最新 release 标记 `cap-v0.5.3`（2026-07-01）。
- 已知坑（Windows 相关，都是 open）：
  - #2019 0.5.6 在 Windows 11 录制中静默崩溃（0xc0000005），**录像丢失且无报错**。https://github.com/CapSoftware/Cap/issues/2019
  - #2151 Windows 窗口录制 bug。https://github.com/CapSoftware/Cap/issues/2151
  - #2002 Windows 屏幕帧不同步。https://github.com/CapSoftware/Cap/issues/2002
  - #1737 Cap 自己的 UI 在 Studio 录像里显示为黑矩形（窗口排除只对 macOS 生效）。https://github.com/CapSoftware/Cap/issues/1737
- 对委托人的价值：**高**。录屏环节里唯一「官方就为 agent 设计」的工具，Claude Code 直接一条 prompt 就能装好 skill + MCP。但要接受 AGPLv3 和 Windows 上的崩溃风险，重要录制建议留 OBS 兜底。
- 出处：https://github.com/CapSoftware/Cap ；https://cap.so/agents ；https://cap.so/docs/installation ；https://github.com/CapSoftware/Cap/pull/1706 ；`gh api repos/CapSoftware/Cap/license`

### OpenScreen（Screen Studio 的开源替代，活跃续作）
- 地址：https://github.com/getopenscreen/openscreen （原仓库 https://github.com/siddharthvaddem/openscreen 已归档）
- 形态：桌面软件 + headless CLI
- 能做什么：录窗口/整屏、麦克风与系统音频；**自动跟随鼠标的放大**（可调深度/时长/缓动）、鼠标光标尺寸平滑与点击特效；录制后路径平滑；背景（壁纸/纯色/渐变/自定义图）；动态模糊；时间线裁剪、变速；文字箭头图片标注；本地离线字幕；**对话式 AI 剪辑助手**（自带 key，支持 Claude/OpenAI/Gemini 等）；导出 MP4/GIF，多比例多分辨率，GPU 编码（Windows 走 D3D11，有 CPU 回退）。
- Windows 支持：官方支持（macOS / Windows / Linux），Windows 上推荐从 Microsoft Store 装，也可下 Releases 里的安装包。原版还提供 `winget install SiddharthVaddem.OpenScreen`。
- AI 助手能否调用：**能**。仓库 README 里有 CLI 一节，明确说是给脚本、CI 和 AI coding agent 用的：`openscreen record --duration 20 --project demo.openscreen --json`、`openscreen export demo.openscreen -o demo.mp4 --json`，输出 NDJSON，可编程改 `.openscreen` 项目 JSON（缩放、标注、裁剪）。
- 开源协议：MIT
- 活跃度：Star 3,404；最近提交 2026-10-01；未归档。（**对比**：已归档的原仓库 siddharthvaddem/openscreen Star 39,956、最后提交 2026-06-17。`EtienneLescot/openscreen` 这个地址现已重定向到 getopenscreen/openscreen，即仓库改名/转移过。）
- 已知坑：README 自己写明「under active development — expect rough edges and occasional breaking changes，包括 `.openscreen` 项目格式和 CLI 都可能变」，不适合当稳定生产依赖。https://github.com/getopenscreen/openscreen
- 对委托人的价值：**高**。这是「录屏后自动跟随鼠标放大 + 加背景阴影」这个需求上，Windows 能用、活跃维护、且带 CLI 的唯一选择；原版 3.9 万星仓库已死，别装原版。
- 出处：https://github.com/getopenscreen/openscreen ；https://github.com/siddharthvaddem/openscreen ；`gh api repos/getopenscreen/openscreen`

- 开源协议：MIT
- 活跃度：Star 66；最近提交 2026-09-05；未归档。

- 对委托人的价值：**中**。如果你要录 30 分钟以上的长教程，它「边录边写盘 + 长录制恢复」这点比 OpenScreen 更对症；但生态小，当备选。

### auto-editor（自动剪掉没说话的片段）
- 地址：https://github.com/WyattBlue/auto-editor ；官网 https://auto-editor.com
- 形态：命令行（Nim 写的单文件可执行程序）
- 能做什么：按音频响度（默认 `--edit audio:threshold=0.04,stream=all`）或画面动态（`--edit motion:threshold=0.02`）自动剪掉静音/静止段；`--margin` 控制剪辑前后留白（默认 0.2s）；可给不同区段打标签做「静音剪掉 + 大声段落 1.5 倍速」这类规则；还能**导出成剪辑软件的工程文件**：Premiere（`--export premiere`）、DaVinci Resolve、Final Cut Pro、Shotcut、Kdenlive，或 `--export clip-sequence` 出素材片段。也内置 skill：`npx skills add WyattBlue/auto-editor`。
- Windows 支持：官方说三平台都有；Release 直接给 `auto-editor-windows-x86_64.exe`（31.0.0 那个包 47MB）。装起来不麻烦。
- AI 助手能否调用：**能，是本次调研里最「agent 友好」的**——纯命令行、非交互、参数固定、确定性输出，天然适合 Claude Code 批量调用；官方还提供 skill 安装命令。
- 开源协议：Unlicense（公共领域）；注意 Release 里的二进制产物可能带其他开源协议，官网/app 的自有素材是专有协议。
- 活跃度：Star 5,400；最近提交 2026-09-19；未归档；最新 release **31.6.0（2026-09-06）**。
- 已知坑：**`pip install auto-editor` 已经不能再用了**——官网安装页明确写 "The auto-editor cli is no longer being published on pip. It is recommended to switch to a different installation method."，要改用官方二进制或其他方式。https://auto-editor.com/installing
- 对委托人的价值：**高**。这是「不露脸技术教程」粗剪环节性价比最高的一步：一条命令干掉所有停顿时段，还能把剪点导出给剪映/达芬奇继续精修。
- 出处：https://github.com/WyattBlue/auto-editor ；https://auto-editor.com/installing ；https://github.com/WyattBlue/auto-editor/releases/tag/31.0.0 ；`gh api repos/WyattBlue/auto-editor`

### pyJianYingDraft（用 Python 生成剪映草稿）
- 地址：https://github.com/GuanYixuan/pyJianYingDraft （PyPI：https://pypi.org/project/pyjianyingdraft/ ）
- 形态：Python 库（`pip install pyJianYingDraft`，当前版本 0.3.0）
- 能做什么：用代码生成剪映草稿（视频/图片素材与时间控制、整体调节、关键帧、色度抠图、背景填充、混合模式、贴纸、文本、特效、滤镜、转场、音频淡入淡出、SRT 字幕等）；模板模式可加载已有草稿、替换素材、改文本；Windows 上还能**自动导出**（依赖 `uiautomation`，把剪映窗口置顶并模拟点击）。
- Windows 支持：Windows 支持草稿生成、模板模式、自动导出全套；**Linux/macOS 只支持生成草稿和模板模式，不支持自动导出**，且生成的草稿最终仍要在 Windows 版剪映里导出。
- AI 助手能否调用：**能**（就是 Python 库，Claude Code 直接写脚本调；另有 MCP 封装见下条）。
- 开源协议：Apache-2.0
- 活跃度：Star 4,469；最近提交 2026-09-26；未归档。（关联项目 pyCapCut：Star 690、最近提交 2026-09-30、**仓库无 LICENSE 文件，协议未核实**。）
- 已知坑（**这条最重要**）：
  - **剪映 6.0+ 草稿加密**。README 写：6+ 对 `draft_content.json` 加密，模板模式「仅支持剪映 5.9 及以下」。用户在 Issue #82 里实测 8.2.0：新建草稿不加密，但做了剪辑操作后会被加密，加密内容是二进制乱码。https://github.com/GuanYixuan/pyJianYingDraft/issues/82
  - **剪映 7+ 隐藏控件，自动导出失效**。README 表格：控制剪映打开指定草稿 / 导出草稿到指定位置 / 调分辨率帧率，在「6.8（剪映 6 及以下）」是 ✅，在「10.8（剪映 7 及以上）」是 ❌；自动导出仅在剪映专业版 **5.9 和 6.8** 实测通过。有 Issue #193「想请问下 高版本剪映 找不到控件 怎么实现自动导出呢」仍在 open。
  - **生成功能也有版本门槛**：open PR #198（2026-09-10，到调研时未合并）指出，剪映 6.0 起草稿主文件已从 `draft_content.json` 改名为 `draft_info.json`，主分支仍写旧文件名，在剪映 11.4.0 上会被判「草稿内容已损坏」；该 PR 同时说明「生成一直可行，只差文件名这一处，内容明文即可，无需实现加密」。https://github.com/GuanYixuan/pyJianYingDraft/issues/198
  - Issue #194「支援 10.8 版本 但是 無法二次修改對嗎?」仍 open，即新版生成后可能改不动。https://github.com/GuanYixuan/pyJianYingDraft/issues/194
  - PR #189「Add local decryption for Jianying 6+ drafts」已被关闭（是否合并未核实），所以「本地解密」这条路目前**不要指望**。
  - `uiautomation` 在部分 Python 版本（如 3.13）有依赖问题，官方推荐 3.8 / 3.10 / 3.11；导出时会抢光标和窗口置顶，建议闲时/夜间跑。
- 对委托人的价值：**中**。它能让 AI 助手直接产出剪映时间轴，价值明确；但版本依赖很脆，要用就得把剪映**锁在 5.9 或 6.8**（Issue #197「5.9版本大伙在哪里下载的」也说明降级不易）。不做版本锁定的话，直接用 auto-editor + FFmpeg 更省事。
- 出处：https://github.com/GuanYixuan/pyJianYingDraft ；https://pypi.org/project/pyjianyingdraft/ ；https://github.com/GuanYixuan/pyJianYingDraft/issues/82 ；https://github.com/GuanYixuan/pyJianYingDraft/issues/198 ；https://github.com/GuanYixuan/pyJianYingDraft/issues/194 ；`gh api repos/GuanYixuan/pyJianYingDraft`

  - issue #103（**PR，open，2026-07-05**）标题就是「CJK caption support, Windows fixes, EDL-level style/audio overrides」，作者自述是在 **Windows 上用 video-use 剪真实中文竖版（小红书）项目**时改的：把 `edl.json` 的 `subtitle_style` 提成可按项目覆盖、CJK 改按短语聚合（遇中文标点或满 10 字断句、字间不加空格、标点全部不显示）、Windows 字幕路径反斜杠归一成正斜杠、overlay 先缩放到基准分辨率再合成。**到 2026-10-01 这个 PR 仍是 open，没合进主分支。**
- 已知坑（除上面已列的）：装 ffmpeg 时如果构建里没有 libass，`--build-subtitles` 会直接抛 `CalledProcessError` 且报错信息看起来像引号问题、不像缺 filter（#118 里在 macOS Homebrew 默认 bottle 上复现）；`SUB_FORCE_STYLE` 只对拉丁字形有效（同上）；官方还提醒「不要在安装验证阶段跑转写，Scribe 是花钱的」。
- 对委托人的价值：**中**。它把「转写驱动剪辑 + 每刀自检 + 跨会话记忆」整套流程做成了 Claude Code 原生 skill，**是本次调研里最接近「AI 助手自己把片子剪完」的一个**，思路与委托人的诉求高度重合。但有三条硬伤挡住它做主力：①转写写死 ElevenLabs，要本地/国内 ASR 得自己 fork（#4 未合，且作者明确反对本地转写）；②中文字幕默认渲染成方块，中文可用路径依赖 #103 / #118 这些**未合并**的补丁；③无官方 Windows 安装路径，Windows 相关 open issue 一堆、合并的只有 1 个。**建议现在不要把它当主力**，而是当「值得 fork 参考的实现」——它把「字幕必须最后烧」「按段提取再无损 concat」「每刀 30ms 淡入淡出」「转写结果按源文件缓存」「别在词中间下刀」这些血泪坑写成了硬规则，可以直接抄进自己的 FFmpeg 脚本，这部分价值与语言/平台无关。

## 拿不准的点

1. **Cap 的 AGPLv3 到底管到哪一步**：LICENSE 说 `cap-camera*` / `scap-*` crate 是 MIT、其余 AGPLv3，但官网文档写 "permissive license"，两边对不上。如果要把 Cap 的代码嵌进自己的闭源产品，需要法务确认。另外 Cap 的录制/导出本身是否依赖登录 Cap 账号，CLI 无账号能否纯本地跑，我**没有实际验证**。
2. **OpenScreen 新仓库的「原班人马」说法**：getopenscreen/openscreen README 说「Development moved here with his approval」、原仓库是 Siddharth Vaddem 主动归档，但我在 GitHub API 上看到 `EtienneLescot/openscreen` 直接重定向到 `getopenscreen/openscreen`（说明发生过改名/转移）。谁是当前实际维护者、治理是否稳定，**未核实**。
3. **剪映加密到底是不是所有版本都加密**：Issue #82 里用户实测 8.2.0「刚开始不加密，剪辑操作后会被加密，新建草稿也处于加密状态」；而 PR #198 说「生成一直可行，只差文件名」。两者不冲突（一个说读模板、一个说写新草稿），但**具体哪些剪映版本生成草稿后能被正常打开，我没能拿到完整的版本矩阵**，只有 pyJianYingDraft README 的「5.9 ✅ / 10.8 🟡」和 PR #198 的「11.4.0 实测」两处数据点。
4. **PR #189「Add local decryption for Jianying 6+ drafts」是否被合并**：gh 显示 state=closed，但我没有确认是 merged 还是 rejected。仓库 README 仍写「6+ 加密、模板模式仅支持 5.9 及以下」，倾向是**未合并**，但严格说这是推断。
5. **几个工具的 Windows 实操可行性没验证**：Cap 在 Windows 11 上有「录制中静默崩溃且丢录像」的 open issue（#2019），LikelySnap / Vuoom 的 Windows 包是否真能跑起来，我都没有实测（按任务要求不安装、不运行）。
6. **Xanthus-Sanslab/jianying-ai-mcp 与 hey-jian-wei/jianying-mcp 的开源协议**：两个仓库都没有 LICENSE 文件（gh 返回 null），前者 README 也没写协议，后者徽章写 Apache-2.0。**都算未核实**。
7. **`video-use` 的中文链路只是「看代码和 issue 推出来的」，我没实跑**：正文条目里的结论依据是主分支代码（转写写死 ElevenLabs、`SUB_FORCE_STYLE` 硬编码 Helvetica）、install.md（无 Windows 一节）和 #118 / #103 / #193 这几个 issue 的复现描述，**我没有真的在 Windows 上装它、也没有实测中文旁白转写质量**。所以「中文字幕会不会真的渲染成方块」严格说是别人复现的结果，不是我的实测。另外 #4（FunASR 本地后端）与 #103（CJK + Windows 修复）都还是 open，**将来合没合会直接改变结论**，要用之前得先看这两个 PR 的状态。
8. **obs-cmd 的 Windows 二进制未实测**：Release 资产名 `obs-cmd-x64-windows.tar.gz` 是实际读到的，但没有验证解压后能否在 Windows 上正常连 OBS 4455 端口。
